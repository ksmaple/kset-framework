组件架构

业务宿主

认证并提供 AgentRequest、AgentBusinessContext；负责模型与真实工具适配、检查点持久化及权威结果查询。具体应用入口待确认。

kset-agent-runtime

AgentRuntime 按调用选模型、Skill 与工具源，冻结工具目录后构建 Kernel；McpAgentToolSource 将 MCP 客户端映射为 AgentTool。

kset-agent-core

AgentLoopKernel 唯一执行循环，管理状态、协议、动作、停止、快照与生命周期事件。

调用方向：业务宿主 → Runtime → Core；Core 经 SPI 回调宿主 Model / Tool / Checkpoint

Core 内部协作

strategy · ReAct 默认生成每轮 ModelRequestprotocol · Codec 准备提示并解码 Decisionmodel · AgentModel 调用外部模型适配器action + tool · Handler 执行动作并生成 Observationstop · StopController 集中判定退出checkpoint + event · 快照写入端口和只读观测

模块关系与构建依据：AgentRuntime.java、AgentKernelBuilder.java、AgentLoopKernel.java。Runtime 依赖 Core；Core 无 Runtime、Spring 或业务存储依赖。

功能范围

项目：kset-framework。Runtime 负责按次组装，Core 负责循环、协议、动作、停止和快照。Model、真实工具、Checkpoint 持久化与权限校验由业务宿主实现；仓库内未发现 Agent 专用数据库表，Checkpoint 默认实现为 noop。图中的“业务宿主”是调用边界，具体 Web/RPC 入口、数据库和线上使用状态均未在本仓核实。

  • 标准能力：任务计划、单工具、工具批次、回答分片、最终回答、交互确认；默认 ReAct 有 planning、acting、evaluating、answering 四阶段。
  • 可选能力：只读依赖工具流、协议 Codec、推理策略、动作 Handler、停止策略、生命周期 Listener、工具源、Skill 与 MCP 工具适配。
  • 范围外：宿主业务权限、MCP 传输、数据库持久化实现、跨节点租约、RAG 检索和业务补偿。

关键类与接口关系

CLS-01 AgentRuntime · 现有类runtime / com.kset.agent.runtimerun、resume、kernel：按次组装。关联 E01、E02。
CLS-02 AgentLoopKernel · 现有类core / looprun、resume、execute：统一循环与状态转换。关联 E03、E09。
CLS-03 AgentReasoningStrategy · 现有接口core / strategynextTurn、validate、afterTurn；默认实现 ReactReasoningStrategy。关联 E05。
CLS-04 AgentProtocolCodec · 现有接口core / protocolprepare、decode；内置 agent-json:v1，可选 agent-json-flow:v1。关联 E07、E15。
CLS-05 AgentModel · 现有接口core / model；宿主实现generate(ModelRequest, AgentExecutionContext)。关联 E06。
CLS-06 AgentActionHandler · 现有接口core / actionhandle；标准处理器驱动 AgentTool 执行。关联 E08。
CLS-07 AgentCheckpointPort · 现有接口core / checkpoint；宿主实现save 快照，默认 noop。关联 E04、E13。
CLS-08 AgentToolSource · 现有接口runtime / com.kset.agent.runtimetools(context)；Skill 与 MCP 适配器提供本次工具。关联 E02。
CLS-09 AgentStopController · 现有类core / stopevaluate、evaluateImmediate；集中停止判定。关联 E14。
  1. REL-01 AgentRuntime → AgentLoopKernel：构建并调用，单次调用对应一个新组装的 Kernel。
  2. REL-02 AgentLoopKernel → Strategy / Codec / Model：依次准备轮次、协议、模型响应与决策。
  3. REL-03 AgentLoopKernel → ActionHandler / StopController / CheckpointPort：动作分发、停止与保存。
  4. REL-04 AgentRuntime → AgentToolSource：获取基础及选中 Skill 工具，冻结目录后传入 Core。

关系均为源码可见的调用或构建依赖，不表示继承或对象所有权。依据：Runtime 组装、Kernel 循环。

E05 形成模型输入

E07 解析与验证决策

动作
codec.decode + strategy.validate
数据
模型响应、协议 ID、pending 动作、容量限制
结果

代码可见。内置 agent-json:v1 解析六类标准动作；无控制标记的普通文本视为最终回答。可纠正协议错误计数、保存快照，再按限制决定是否下一轮。依据：AgentJsonV1Codec.java:33-142、AgentLoopKernel.java:300-350。

E08 标准动作分发

动作
task_plan / tool_call / tool_batch / answer_chunk / final_answer / confirmation
数据
callId、taskId、toolName、arguments；工具上下文带幂等键
结果
AgentActionResult

代码可见。可执行的标准工具动作在分发前先写带 pending 与核验标记的 RUNNING 快照；需确认的工具先暂停，批准后才分发。独立工具批次默认使用 Core 共享的 8 线程、64 排队位有界执行器并行提交，队列饱和时并行度下降；宿主可覆盖执行器。真实权限与持久幂等由工具适配器负责，Runtime 可将 MCP 客户端包装为工具。依据：AgentLoopKernel.java:433-447、AgentKernelBuilder.java:176-184、StandardActionHandlers.java:87-252、CLS-06。

E15 可选只读工具依赖流

动作
agent-json-flow:v1 → tool_flow
数据
dependsOn、$toolResult、JSON Pointer、只读工具目录
结果
同层并行，失败或引用缺失阻断下游

代码可见，只有 Builder 调用 readOnlyToolFlow 且请求选择相应协议时启用。处理器先整批核验 readOnly=true 且 requiresConfirmation=false，再按依赖分层执行；写入工具整批拒绝。该路径不提供写入副作用的 pending 快照或结果未知核验。依据：AgentKernelBuilder.java:111-150、ToolFlowActionHandler.java:62-115、协议说明、CLS-04。

E09 状态推进

动作
state.apply + checkpoint + stop 评估
数据
Observation、属性写入或删除、轮次与进展计数
结果
继续下一动作、下一轮或停止

代码可见。计划保存任务；回答分片积累文本；最终回答完成任务。每个动作应用后触发生命周期观测、停止判断和检查点；工具结果供后续 ReAct evaluating 使用。依据：AgentLoopKernel.java:407-463、StandardActionHandlers.java:263-295。

E10 正常出口

动作
finish / AgentResult
数据
runStatus、answer、stopDecision、snapshot
结果
COMPLETED；最终回答在 answer

代码可见。最终回答动作使状态完成，停止前写终态快照并通知监听器。SUSPENDED 的提示位于 suspensionMessage / stopMessage，不写入 answer。依据：AgentLoopKernel.java:493-502,545-550、AgentStopController.java:23-33。

E11 审批等待

动作
confirmation / 危险工具确认
数据
confirmationId 或 callId、完整 pending 动作
结果
SUSPENDED；宿主输入批准或拒绝后恢复

条件路径，代码可见。无审批决定的恢复被拒绝；拒绝生成 Observation，危险工具不执行；批准后首个模型动作须重述 pending 操作。审批不等于业务授权。依据：StandardActionHandlers.java:87-102,297-315、AgentResumeReconciler.java:64-164。

E12 结果未知

动作
暂停核验
数据
完整 pending 工具身份与已有 Observation
结果
RECONCILIATION_REQUIRED + SUSPENDED

条件路径，代码可见。有副作用工具返回未知、异常或空结果，以及批次超时等无法确认结果时，保留 pending 并暂停。取消 Future 不保证已启动副作用停止；宿主必须查权威结果。依据：StandardActionHandlers.java:195-228,325-368、AgentLoopKernel.java:419-424,885-905。

E13 核验后恢复

动作
AgentRuntime.resume → AgentResumeReconciler.apply
数据
当前可信业务上下文、原 agentRunId、快照、每项权威 Observation
结果
校验身份，清理 pending，再进入下一模型轮次

条件路径，代码可见。核验快照不接受空输入；Observation 必须完整匹配 callId、taskId、toolName。恢复时重新提供业务上下文和可解析的工具目录。宿主如何查询权威结果待确认。依据：AgentResumeReconciler.java:35-62、AgentRuntime.java:95-106。

E14 停止与故障

动作
AgentStopController / fail
数据
取消、中断、超时、轮次、协议错误、无进展、策略与技术异常
结果
CANCELLED 或 FAILED，返回 stopDecision / failure

条件路径，代码可见。停止控制器统一检查硬限制，再调用宿主策略；活动循环技术异常转为失败结果。检查点失败阻止继续推进。依据：AgentStopController.java:19-121、AgentLoopKernel.java:534-565、CLS-09。

结果与恢复路径

主流程：E01 → E02 → E03 → E04 → E05 → E06 → E07 → E08（或可选 E15）→ E09；没有终态动作时进入下一轮，最终回答经 E10 返回。审批分支：E08 → E11，宿主给出批准或拒绝后再走 E01/E03；拒绝产生 Observation，批准要求模型完整重述 pending 动作。未知结果分支：E08 → E12，宿主按原 (agentRunId, callId) 核验并以完整权威 Observation 经 E13 恢复。协议错误可纠正并计数后再循环；取消、时限与硬限制经 E14 停止。源码可见的调用不代表已在生产运行。

适用边界

并发保护：Kernel 的单次状态为调用局部；共享 Model、Tool、Listener 等需由宿主保证线程安全。工具写入的幂等身份为 (agentRunId, callId)，真实持久化、同键异参校验和跨节点控制由宿主实现。图中未核实任何互斥锁，不能把批次 Executor 当作锁。数据存储：本仓只定义 CheckpointPort，未发现 Agent 专用表或持久化实现。评估建议：无。变更类型与完成状态：不适用。本页说明源码可见行为，不代表已在生产运行或通过验收。
