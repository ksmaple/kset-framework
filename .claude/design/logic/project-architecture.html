架构边界

这是多模块框架库，不是可直接启动的业务应用。根 pom.xml 聚合 16 个子模块；kset-boot-parent 管 Java、Spring 与依赖版本。各 starter 被业务宿主选择引入，Spring 自动配置再按 classpath、Bean、配置和 Web 类型生效。上图分段显示互相独立的典型路径，不能把所有行理解为同一次请求或同一进程。

角色：框架维护者维护模块契约和版本；业务服务选择 Starter 并提供业务控制器、数据表和配置；Gateway 宿主独立处理 WebFlux 流量；外部客户端发起 HTTP；Nacos、数据库、Redis、RocketMQ 与下游 Dubbo 服务只在相应能力启用时出现。具体业务宿主及其部署拓扑待核实。

交互与依据

A01 构建基线

动作
宿主 Maven 引用父 POM 或 BOM
数据
Java 21、1.0.17-SNAPSHOT 与受管依赖版本
结果
模块保持同一编译/依赖基线

代码可见：根 POM 是聚合器；父 POM 是版本管理构件，不参与运行时请求。依据：根 pom.xml、kset-boot-parent/pom.xml。

A02 共享模块与依赖

动作
业务服务选择 Starter，Maven 解析依赖
数据
common 公共能力；cloud 规则 SPI
结果
被选择模块进入宿主 classpath

代码可见：多数 Starter 直接依赖 common；nacos、sentinel、dubbo、gateway 直接依赖 cloud，cloud 再依赖 common。auth 对 redis/web、redis 对 cache/web、dubbo 对 web 的依赖是 optional，不表示默认必装。依据：各子模块 pom.xml，模块结构。

A03 Servlet 服务装配

动作
业务服务加载 Web/Auth/Monitor 自动配置
数据
classpath、配置、Servlet 类型
结果
按条件注册过滤器、鉴权、响应和监控组件

代码可见：web 与 auth.web 只对 Servlet Web 应用生效；monitor 按 classpath 装配 Servlet、Dubbo、Gateway 等链路组件。依据：Web 自动配置、Auth Web 自动配置、Monitor 自动配置。

A04 Gateway 独立宿主

动作
Gateway 宿主加载 WebFlux Gateway Starter
数据
路由、灰度、可选鉴权/Sentinel 配置
结果
注册 GlobalFilter、路由与错误处理

代码可见：Gateway AutoConfiguration 以 Gateway classpath 和开关为条件。项目文档要求 Gateway 与 Servlet Web 分开部署；当前仓库没有应用主类证明任何具体部署已运行。依据：Gateway 自动配置、Gateway README。

A05 数据能力装配

动作
业务服务按需引入 datasource/cache/redis
数据
DataSource、Cache SPI、RedisTemplate
结果
注册元数据填充、L1 缓存或 Redis 能力

代码可见：datasource 在 MyBatis-Plus classpath 下配置自动填充；cache 提供 Caffeine L1 与门面；redis 在 KsetRedisService 存在且 cache API 在 classpath 时注册 RedisKsetCacheStore 为可选 L2。依据：Datasource、Cache、Redis L2。

A06 事件与调度装配

动作
业务服务按需引入 MQ 与 Schedule
数据
EventFacade、RocketMQClientTemplate、DataSource
结果
本地事件或 RocketMQ 实现；有 DataSource 时可装 SQL 任务锁

代码可见：common 的 SpringEventFacade 是缺省 EventFacade；mq 在 RocketMQClientTemplate 存在时先于 common 装配 RocketMqEventFacade。schedule 的 TaskLockProvider 需要 DataSource。依据：Common Event、MQ Event、Schedule。

A07 Agent 内核显式构建

动作
宿主构建 AgentLoopKernel
数据
AgentModel、ToolRegistry、CheckpointPort 等扩展
结果
框架无关的 run/resume 内核

代码可见：agent-core 无本仓内部依赖，无 Spring 自动配置；默认 ReAct 与 agent-json:v1 由 Builder 组装。独立详细链路见 Agent Core 现状说明。依据：AgentKernelBuilder、agent-core POM。

A08 Cloud 共享契约

动作
Nacos/Sentinel/Dubbo/Gateway Starter 引用 cloud
数据
NacosConfigConvention、CloudRuleProvider、GrayTagResolver
结果

代码可见：Cloud 为规则 SPI 和命名约定层，具体加载和流量动作留在各 Starter。依据：Cloud README、Cloud POM。

A09 注册 Nacos 规则监听

动作
Nacos Starter → ConfigService，进程内客户端调用
数据
appName、group、Gateway/Dubbo route dataId
结果
存在 ConfigService 和 Provider 时注册监听

代码可见：KsetCloudRuleRegistrar 对 Gateway 与 Dubbo 路由规则注册 Nacos Listener；ConfigService 缺失或 Providers 为空则返回，注册失败只记录警告。Sentinel 和 Gateway 自身另有规则加载配置。依据：CloudRuleRegistrar。

A10 规则变更回调

动作
Nacos ConfigService → 云 Starter，配置变更回调
数据
JSON 规则内容与 CloudRuleType
结果
同类型 CloudRuleProvider.onRuleChanged

代码可见：监听器收到配置后筛选规则类型并回调 Provider。它是配置事件，不是每个业务请求都会访问 Nacos。依据：KsetCloudRuleRegistrar、CloudRuleProvider。

A11 外部请求

动作
HTTP 客户端 → Gateway 宿主，Web HTTP 同步
数据
URI、Header、可选 Trace/灰度标签
结果
进入 WebFlux Gateway 流程

代码可见：Starter 提供 Gateway 过滤器和路由能力；具体业务 URL 与客户端身份由宿主决定，本仓不能核实。直接访问 Servlet 服务而不经过 Gateway 也是可能的宿主部署方式。依据：Gateway README。

A12 Gateway 过滤与路由

动作
Gateway 宿主 → Gateway Starter，进程内调用
数据
路由规则、GrayTag、可选 Auth/限流
结果
放行并选路或返回错误响应

代码可见：默认 auth-enabled=false 时使用 PassThroughGatewayAuthProvider；启用后才注册 AuthGatewayFilter，并可替换 GatewayAuthProvider。动态路由由 RouteDefinitionRepository 和规则 Provider 更新。依据：Gateway 自动配置。

A13 下游 HTTP 转发

动作
Gateway 宿主 → 业务服务，Web HTTP 同步
数据
路由匹配后的请求、Trace/灰度 Header
结果
到达业务服务或返回网关错误

代码可见：Gateway Starter 提供路由和灰度过滤器；具体下游 URI 来自宿主/Nacos 规则，不在本仓固定。与 Dubbo 直连 RPC 是不同通信路径。依据：Gateway 自动配置、路由规则 Provider。

A14 Servlet 横切入口

数据

代码可见：Auth 的 LoginAuthFilter 注册到 Servlet；Monitor 的 TraceIdFilter 和 Web 的响应/异常组件各按条件装配。图不主张这些独立过滤器之间未核实的精确执行顺序。依据：AuthWeb、TraceIdFilter、Web。

A15 控制器结果

A22 定时任务唯一运行锁

动作

数据

A23 无数据源退化

动作

结果

代码可见：缺少 DataSource 时注册启动告警，不会建立 JDBC 锁提供者。宿主不能把此情形当作跨实例单活。依据：ksetTaskLockMissingWarner。

数据

代码可见：Core 只定义端口及同步循环，外部模型网络请求、工具副作用、快照存储与权限由宿主实现；本仓不指定 Agent 快照数据库和表。依据：AgentKernelBuilder、AgentCheckpointPort。

A26 统一优雅启停

动作
Common SmartLifecycle → 当前宿主组件
数据
相位、shutdownTimeout、readiness
结果
摘流后按相位排空组件

代码可见：readiness 600、流量 500、事件 400、线程池 300、监控 200、基础设施 100；按相位升序启动、降序停止。各宿主进程分别执行该逻辑，不是仓库集中控制所有部署。依据：Lifecycle 自动配置、生命周期相位。

范围与注意事项

覆盖根 POM、16 个子模块、直接内部依赖、Spring 自动配置入口、代表性的 HTTP/RPC/配置/数据/消息/调度/Agent 路径及统一启停。图上跨进程通信明确写作 Web HTTP、Dubbo RPC、Nacos 配置回调或 RocketMQ 投递；同一宿主内的 Starter 调用是进程内。具体业务数据库表、HTTP 路由、Dubbo 服务方法、Nacos 实例和真实部署拓扑不在本仓，待宿主核实。

本次未覆盖各模块全部配置项、第三方框架内部实现、业务侧权限规则、生产运行验证和外部 kset-rag 项目源码。现状说明只标注代码可见路径；本次变更类型与交付完成状态不适用，评估建议：无。
