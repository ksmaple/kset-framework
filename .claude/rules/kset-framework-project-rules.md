# kset-framework 项目规则

> init 生成的项目专属规则。本文件不复制平台规则，声明目标项目 coder、fixer 与独立测试任务的共用执行边界。

R001: `kset-framework-coder` 仅负责修改任务相关的源代码、代码配置、接口契约、正式 SQL 脚本、project-spec、`docs/{module}/changes/` 功能变更记录及按 R158 需同步的已有文档；用户要求保存正式模块说明或业务设计时按 R178–R180 处理，要求独立保存其他材料时可按 R141–R142 写入实施或迁移计划、现状分析报告及 SQL 设计材料
R002: `kset-framework-coder` 禁止执行测试命令、测试类、测试脚本或测试任务
R003: `kset-framework-coder` 禁止启动应用、服务、容器、开发服务器或其他项目运行进程
R004: `kset-framework-coder` 仅在用户当前对话明确要求编译时允许执行编译
R005: 任务描述、CI、默认验收流程或工具参数不得替代 R004 的用户授权
R006: R004 授权的编译范围仅限最小 compile-only，不包含测试、打包、安装或项目启动
R007: `kset-framework-coder` 实现配置、字典、元数据，或频繁读取、可复用的常见查询时，须自动评估缓存候选并优先复用项目现有缓存框架或缓存用法
R008: 缓存候选须同时满足读多写少、调用重复、Key 空间有界与业务可接受明确短时陈旧
R009: 仅进程内使用、数据量有界且不要求跨节点一致的数据可使用项目现有本地缓存方式
R010: 跨节点共享或要求多实例一致视图的数据须使用项目现有分布式缓存方式
R011: 权限、余额、库存、额度、订单状态等强一致或实时查询默认禁止缓存，除非已明确 Key、TTL、失效、并发回源与权威数据源回退策略
R012: 项目无适用缓存能力时，新增缓存依赖、中间件或基础设施须先获得用户明确授权
R013: `kset-framework-coder` 对同一功能再次调优或替换实现时，须创建或更新 `docs/{module}/changes/{feature-key}.md`
R014: 功能变更记录须包含稳定 change-id、当前入口、相关文件与符号、替代关系、实现状态、回滚目标、清理条件、基线与结果 Git ref、回滚来源及可用性
R015: 功能变更记录只允许保存项目内相对路径与轻量说明，禁止复制源码正文、构建产物、日志或敏感配置值
R016: 新实现接管入口后，已移除的旧实现须标为 removed，仍承接旧调用方的实现须标为 active-compatible
R017: 本次功能更新或修复替换旧实现后，须核对静态引用、动态调用、配置入口及对外契约；确认无生产调用、兼容迁移完成且属于本次授权替换范围时，同次移除不再使用的旧代码，在变更计划中列出受影响入口与回滚影响，并更新适用的功能变更记录。仍承接旧调用方的实现须保留，已暴露 RPC 按 R117 分阶段退役
R018: 变更收尾须排查本次涉及目录的代码、文档和关联产物，区分有效、可再生成、已确认废弃与待核实内容；删除前核对归属、静态及动态引用、替代迁移、兼容边界和恢复依据，在本次授权范围内按具体路径定向清理，同步索引、链接和适用的功能变更记录，复查残留、断链及 Git 状态。目录须核实全部内容，链接不得递归清理目标；不得仅凭名称、时间、后缀、体积或 Git 状态判废，不得全仓清扫。历史范围外内容先列路径、依据和回滚影响并另行授权；生产数据、正式发布制品、审计记录和唯一恢复备份遵守保留策略与专项授权。
R018a: 变更收尾须按既有目录约定检查项目根目录及本次涉及子目录中的错放文件、重复副本、孤立文档、过期入口、无归属临时目录和无用途空目录；有效内容优先归入既有权威目录，迁移前核对同名冲突及静态、动态路径依赖，迁移后修复引用、导航和配置。共享资源、用户指定位置及仍有消费者的文件不机械归并，不新建平行目录或保留重复正文；范围外问题只报告位置、依据及建议。交付区分已归位、已删除、明确保留与待核实项，不以文件数量或目录深度单独判定整洁程度。
R018b: 临时数据、一次性生成或排查脚本、打包文件、构建输出及其旧版本须按用途设置有界的数量、总体积或保留期限，不得无限累积；未约定时本次一次性内容在任务结束后清理。新版核验有效且旧版无消费者、引用或已确认回滚用途后，按删除规则定向清理旧产物、失效清单和空目录；大型产物优先核对，保留历史版本须说明用途、保留边界及清理条件。正式维护的源码脚本和仍被消费的数据不自动删除；正式发布制品、审计记录和唯一恢复备份按保留策略及专项授权处理。
R019: 功能回滚须由用户选择目标 change-id，并按记录指定的 Git ref 恢复入口关系、配置和必要文件
R020: `kset-framework-coder` 实现有副作用的请求、定时任务、消息消费或共享数据修改时，须优先检查业务方法重复执行、并发执行与异常中断造成的重复生效、漏执行或结果误判
R021: 发奖、资金或积分权益变化、不可逆外部副作用及用户接口的一次性提交，若同一业务操作重试会重复生效，须以稳定业务单号、状态条件或唯一约束保证只生效一次；仅需识别同键异参时保存参数指纹
R022: 适用请求幂等时，须由持久化结果、唯一约束或条件写保证只有一个执行者生效；查询、目标状态设置及业务明确允许每次触发累加的计数或榜单投影不机械增加幂等或去重
R023: 请求正确性禁止仅依赖前端防重复、网关去重、进程内状态、本地锁或分布式锁
R024: 远程结果未知时须按原业务单号查询权威结果，确认未执行后才允许有限重试
R025: 定时任务须核对部署实例数、调度器互斥保证和业务并行口径；多实例可能同时执行且任务按单执行者设计时，默认使用 R157 的适用 Redis 锁。调度器已有经核实的互斥保证、任务按分片并行或业务允许并行且有独立结果保护时，不重复加全局锁；不得以单机状态作为唯一保障
R026: 全局单例任务优先复用项目现有分布式调度互斥或适用 Redis 锁；无适用 Redis 时按已确认能力选择数据库租约等替代方案，新增基础设施须遵守 R037
R027: 业务数据任务按实际并发范围选择任务、分片或记录级保障；允许多实例分片处理时不得用长时间全局锁串行包住整批处理，同一记录并发会造成业务错误时仍须以原子抢占或条件写保护结果
R028: 数据库租约须包含 owner、过期时间与 fencing token，过期持有者提交前须被持久化条件拒绝
R029: 批量任务须使用稳定排序与有界批次；确需多语句原子提交且按 R078 获授权时使用独立短事务，禁止在全量扫描或远程调用期间持有事务和锁
R030: 数据实现须明确唯一权威数据源
R031: 权威价值变化与不可违反的本地业务不变量须由最小必要的事务、条件更新、原子增减或唯一约束保证；可补救或可重建的附属结果按失败后果选择保护，不机械叠加 CAS、锁、事务或去重表，不得因此丢失须逐次计入的变化
R032: 跨服务操作须保持正常路径的权威事实、幂等边界和真实结果；系统重启、发布切换、RPC 断联或 MySQL、Redis、MQ 等低概率基础设施故障造成的残留流程或数据问题，未有已确认的系统自动修复承诺时，在设计中明确人工定位、处理责任和结果核验，不新增推测性补偿状态、表或流程。已明确要求自动修复时先复用现有对账补发能力，仍不足才按风险设计可靠投递或补偿；附属异常沿用既有处置，禁止跨服务长事务或分布式大事务
R033: 写入确认、幂等判断和补偿核验禁止依赖可能延迟的只读副本、缓存或搜索索引
R034: 数据修复须幂等、可续跑且可审计
R035: 多租户查询、唯一键、幂等键、缓存、任务分片与租约须包含租户维度
R036: 调度窗口、租约、过期与对账时间须使用项目约定的共享权威时钟和明确时区
R037: 分布式实现须优先复用 project-spec 与项目源码中的现有能力，新增调度器、锁服务、中间件或基础设施须先获得用户明确授权
R038: `kset-framework-coder`、`kset-framework-fixer` 与独立测试任务在代码研发、修复和测试代码处理阶段默认禁止编译项目
R039: 用户当前对话明确要求编译验证时，仅允许执行本次变更所需的最小 compile-only 编译
R040: 编译验证授权禁止扩展为测试、打包、安装、启动、预览、发布或部署
R041: `kset-framework-coder`、`kset-framework-fixer` 与独立测试任务默认禁止启动或运行应用、服务、容器、开发服务器与 H5 预览服务器
R042: `kset-framework-coder`、`kset-framework-fixer` 与独立测试任务默认禁止执行 H5 或前端生产构建、打包、上传、发布与部署
R043: 用户当前对话明确要求部署并指定目标环境后，方可执行该目标部署必要的构建、打包、上传、发布与目标服务启停
R044: 部署授权禁止扩展到未指定环境、无关模块、运行测试或本地开发服务器
R045: `kset-framework-fixer` 或独立测试任务仅在用户当前对话明确要求运行测试时执行约定的最小测试目标及其进程内测试上下文；若触发未授权编译、独立应用或服务启动、预览或部署则须停止并说明
R046: `runCompile`、`runTests`、任务描述、CI、配置文件、工具参数与项目默认流程均不得替代用户对编译、测试、运行或部署的当前对话授权
R047: `kset-framework-coder` 发现兼容风险时须依据发布、部署、标签、生产调用、调用方迁移与功能变更记录自动判定开发未上线或已上线，证据缺失或冲突时才询问用户
R048: 每次上线状态判定须记录判定时间、结果、证据、基线 Git ref 与当时入口、契约、调用方、迁移状态和实现状态
R049: 上线状态须作为对应 change-id 的时点快照保留，后续上线、回滚或再次迭代禁止回写历史状态
R050: 用户对完整变更计划、修复计划或任务清单整体明确授权后，授权范围内全部已确定步骤视为已获执行授权，无须逐步重复确认
R051: 已获整体授权的确定步骤须按依赖顺序连续执行
R053: 多步骤任务仅当任务清单全部为 completed 且验收标准全部核验通过时，方可宣告完成并输出完成型最终答复
R054: 任务清单存在 pending 或 in_progress 且仍有已授权可执行步骤时须继续执行
R056: blocked 状态不属于任务完成，返回时仅可报告阻塞原因、已完成范围与恢复条件
R057: 阻塞解除后须恢复原任务清单并继续执行未完成项
R058: `kset-framework-coder`、`kset-framework-fixer` 与独立测试任务在处理代码、SQL、配置或依赖前须读取 project-spec 的「构建与基础设施兼容基线」
R059: 实现与修复须兼容基线中登记的实际版本和模块归属；多版本组件按目标模块锁定，受父 POM/BOM 管理的依赖禁止脱离依赖管理自行覆盖
R060: 未经用户当前对话明确授权，禁止升级、降级、替换、跨模块混用基线外版本，或使用基线版本不支持的语法、API、SQL、配置项和协议能力
R070: Git 提交信息默认使用中文；用户仅提供英文内容说明时须归纳或翻译为中文，只有明确指定其他语言时才按其要求生成
R070a: Git 仓库的开发、修复与文档修改按项目明确的分支规则执行；项目未规定主分支开发时，在任务分支的独立 worktree 开展任务；项目初始化仅在经 Git 确认的主工作树执行，临时目录按 R106 排除
R070b: 修改、暂存、提交或推送前须确认目标仓库、当前工作树路径、绑定的非游离分支及现有未提交路径，不得以目录名称推断工作树归属
R070c: 项目未明确规定只在主分支开发时，同一任务须沿用本会话对应且仍存在的任务分支；用户明确删除该分支后解除会话归属，不自动复用同名远端分支，后续改动重新按主题选择分支；新任务也须按主题选择任务分支，无合适分支时仅从已确认的正式线上主分支按项目命名规范创建全新任务分支，复用已有远端任务分支时可建立同名本地跟踪分支；未约定命名时使用 `<type>/<version>-<feature>`，type 为 feat、fix 或 perf，版本不明时以 `YYYYMMDD` 替代 version
R070d: 项目未明确规定主分支开发时，首次修改前须复用任务分支已有 worktree；缺少时优先按本项目已确认的 worktree 目录约定创建，未约定则默认位于 `<工作区根>/worktree/<目录组>/<任务键>`。工作区根优先取已确认位置，缺省取仓库主工作树父目录；单模块任务的目录组取模块目录名，其他任务取仓库目录名，与其他仓库重名时使用可区分仓库的稳定标识；任务键优先取用户指定目录名，否则取 `<仓库目录名>-<任务主题短名>`。创建时固定目录组与任务键，核对为安全单层目录名、目标路径在已确认根内且未被占用，后续范围变化不重算；已有绑定路径可沿用，迁移须用户明确要求
R070e: 当前工作树含无关未提交变更时须识别归属并避开，不得覆盖、暂存、提交或搬移无关内容
R070f: commit 与 push 默认仅在用户当前对话明确要求时执行；普通提交目标为任务分支，普通推送目标为对应的 `origin/<任务分支>`；本次获授权合并成功后，用户明确要求推送已确认的集成目标时，才可推送该目标的对应远端分支；项目明确规定主分支开发时按项目规则确定目标，明确自动提交流程按其限定范围执行
R070g: merge 仅在用户当前对话明确要求且已确认来源和目标时执行
R070h: commit 或 push 后须核对仍位于执行前工作树与分支；merge 及获授权的目标推送后须返回本会话原功能分支的 worktree，核对路径与分支并仅保持同一任务的后续改动归属，无会话功能分支时返回执行前工作树
R070i: 未经用户明确要求，禁止删除已有分支或 worktree
R070j: 合并须直接在目标分支已有 worktree 执行；不得为合并另建专用分支
R070k: 现有其他分支或 worktree 的未提交内容须保留，不得擅自搬移或覆盖
R070l: 项目明确规定主分支开发时，须在项目指定的主工作树和分支修改；路径不符时停止写入并说明
R070m: 仅凭目录名不能判断工作树或分支归属，须以 Git 信息核实
R070n: 开发或修复首次修改前须完成 R070b–R070d 的检查
R070o: 同一任务已归属现有任务分支时，其修复或后续改动须继续使用该分支及对应 worktree，不得因改动类型或该分支已合并而新建分支；项目明确只在主分支开发时按项目规则执行，并遵守 R070e 的变更归属边界
R071: 数据库索引设计须依据实际业务唯一性约束或 WHERE、JOIN、ORDER BY、GROUP BY 访问路径，禁止仅因字段或参数存在而建索引
R072: 稳定业务唯一键须优先使用唯一约束或唯一索引保证
R072a: 多租户数据的业务唯一键须包含租户隔离维度
R072b: 存量表新增唯一约束前须检查并处置重复数据
R072c: 唯一约束须明确逻辑删除记录是否继续占用业务键，并使用目标数据库版本实际支持的方案
R073: 用户、类型、状态和时间等真实查询维度可按访问路径建立组合索引
R073a: 类型、状态、deleted 等低基数字段禁止脱离高选择性维度机械建立单列索引
R073b: 时间列用于范围过滤、时间排序或游标时须放在相关等值过滤列之后；时间等值过滤按 R076 的等值列顺序设计，并以实际查询路径和执行计划验证
R073c: 仅明确的全局时间窗口、归档清理或时间排序查询允许单独建立时间索引
R074: 金额、余额、金币、积分、库存、额度、价格、数量、变更值、差值与增减量等值类字段禁止作为普通索引列
R075: 仅用于写入、展示、计算或请求透传且不参与查询条件与唯一约束的参数字段禁止建索引
R076: 组合索引须将稳定等值与高选择性维度置前并将范围或排序时间列置后
R076a: 新增索引前须排除被主键、唯一索引或现有组合索引左前缀覆盖的冗余索引
R076b: 索引数量须保持完成约束与核心查询所需的最小集合
R077: 索引变更须使用目标数据库执行计划结合数据量、基数与写入成本验证
R077a: 普通索引禁止替代本应由唯一约束保证的业务不变量

R167: Redis Lua 上线前须按数据规模核对执行步骤、Key 与成员数量、返回量、节点 CPU/内存和延迟预算，禁止无界循环、全量遍历、大批量返回及阻塞或长时间运行；脚本错误不保证此前写入回滚，须明确部分写入的恢复口径。上线后按慢日志和监控核对脚本耗时、节点负载、超时与失败，超预算时停止或回退方案
R168: 新增表字段须按业务值域、精度、长度、空值与默认值语义选择目标方言支持的类型；固定精度小数采用长整型定点存储时须使用对应整数列，注释写明缩放单位和小数位，无法无损承载时按实际精度选型。字段注释还须写明含义及枚举口径；非空列不得用伪造默认值掩盖缺失，存量表加非空列须明确回填与约束顺序。大文本、二进制或 JSON 字段按实际大小与访问频率决定是否拆分，避免高频列表无用途地读取、排序或索引大字段
R169: 在线列表、分页、批量、关联和导出查询须显式选择必要列，禁止 `SELECT *` 和无界返回；大字段仅在确需的详情或专门读取路径取回。查询须有适用的租户及业务隔离条件、结果上限和稳定排序，深分页按项目数据量与性能预算选择游标或有界 `OFFSET`，动态值参数化、动态排序字段走固定允许列表
R170: 设计和修复索引查询须核对列与参数类型、字符集或排序规则、组合索引最左前缀及实际谓词；函数、表达式、隐式转换、前置通配 `LIKE` 和跨列 `OR` 等可能改变访问路径的写法须用目标版本的执行计划与数据分布核实，不凭索引存在断言有效。高频或慢查询须核对扫描行数、回表、排序、临时结果、锁范围和写入成本
R171: 写事务内只允许为本地不变量所必需的有界条件读取，须核对索引、隔离级别、锁定范围及所有入口的加锁顺序；普通纯查询仍按 R078d 不显式开启事务。读取后写入须以条件写、唯一约束或必要锁定读取在提交时守住并发条件，异常须按项目框架回滚，不得吞异常后误提交或把外部副作用放进事务
R172: 死锁与锁等待超时须按数据库错误码和可用证据区分，核对扫描范围、相反锁顺序与事务时长，有可修正原因时先修正；仅在原事务完整回滚且整次操作可安全重做时，对可识别的瞬时错误做有上限、带退避的整事务重试。唯一键冲突、业务状态冲突、外部副作用及写入结果未知不得盲目重试
R173: 新增或修改文本文件及文件导入导出时须明确源文件、传输和目标文件的格式与字符编码，项目内部文本默认 UTF-8 无 BOM；外部契约或消费者明确要求其他编码或 BOM 时按边界转换并记录依据。涉及中文须核对从原始字节到解析、展示及导出回读的结果，禁止依赖系统默认编码、静默接受乱码或对乱码字符串反复转码；无法运行验证时标明未验证范围
R175: 项目规范形成文件前须确认所属项目、产出规范、用途、格式与正式交付或本地协作的 Git 类别；固定专项文件按 R140、其他已定义协作类别按 R141–R142，正式模块说明与业务设计按 R178–R180，已选文档交付规范组按项目内产物契约与配置执行。没有固定文件契约的结果默认在对话中交付，仅在用户要求保存时按实际用途选择路径；不得为满足分类目录预建空文件，也不得因规范参与生成而忽略正式项目交付
R176: AI 协作文档与过程产物按实际职责管理，不再创建或写入项目根 `artifacts/` 等历史产物目录；已确认的协作规则在独立项目规则正文维护，角色流程在项目规范正文维护，正式文档按 R140–R142 管理，待评审规则候选和临时证据进入 `tmp/drafts/`，不得因生成或目录存在而视为生效规则、审批或运行事实。历史材料迁移前须核对内容、消费者与恢复依据，迁移后核对字节或 hash 并修复入口、生成路径和 Git 排除配置，再按 R018–R018b 定向清理；唯一恢复备份保留至恢复需求解除且所需材料已有完整持久备份，Git 忽略材料的跨工作区恢复不得仅依赖 Git
R177: 修改项目代码与配置时须核对 `project-spec.md` 中有来源的构建版本、模块和技术基线，并在受影响模块保持兼容；init 自动提取的规则候选仅供审阅，未确认的文档原句、依赖线索或运行状态不得作为已生效项目约束
R178: 用户要求新建正式模块说明时，以已核实的 Maven 或功能模块名为 `{module}`，写入仓库根 `docs/{module}/overview/README.md`；说明模块职责、适用场景、能力边界、关键入口、依赖与扩展点，并区分现有实现和拟议能力。模块内 README 保留紧邻源码的接入与构建说明，双方通过链接定位各自权威内容，不复制同一主题正文；不因目录约定为所有模块预建说明
