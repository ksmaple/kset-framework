# kset-framework-coder

> 项目约定见 [project-spec.md](references/project-spec.md)。init 仅生成本项目的 coder/fixer，不迁移平台公共技能。


| 项    | 值                 |
| ---- | ----------------- |
| proj | `kset-framework`          |
| 类型   | **backend** |


## 触发条件

**启用**：在本仓完成项目内设计、实现功能、修改业务源码、按 project-spec 编码。

**不启用**：编译/测试失败修错 → `kset-framework-fixer`；平台 init → 平台仓 `kaka-utils-project-init`。

## 核心规则

R001: 先读 project-spec.md，再对照本仓源码与现有契约
R002: 项目约定以 project-spec 为准；未登记事项优先沿用本仓现有做法
R003: 项目内设计与业务代码实现只使用本技能，不依赖未生成的平台公共技能
R004: 新模块的架构、API、数据、时间格式及关键目录约定须先写入 project-spec
R005: 禁止把平台仓库外绝对路径或外部引用作为未确认的可执行依赖
R006: project-spec 与存量实现不足以确定方案时须先向用户确认
R007: 本技能默认验收标准为文件逻辑完成与静态自查
R008: 编写类名、方法名、API 操作名及入参/出参字段时须简单易懂，优先业务人员可理解的日常用语，避免晦涩缩写
R009: 改码前须先输出变更计划并获用户授权，禁止未经确认直接改文件
R010: 验证方式仅按用户当次要求与项目已有能力决定
R011: 任务涉及外部文档、外部项目或跨仓文件时须先读取 project-spec 外部引用记录，并仅补充名称、位置、用途与关联目录
R012: 外部引用记录禁止复制外部正文或写入凭据、令牌和敏感查询参数
R013: 修改已有功能时须优先将新增或变化逻辑实现为职责单一的新方法，并在原入口方法的适当位置插入调用；禁止在原方法体内持续堆叠新逻辑
R014: 原方法本身属于核心逻辑且无法仅插入调用时，须先将修改前逻辑完整抽取为最小可见性且以 `ForRollback` 结尾的回滚保留方法，并在方法上方注明保留原因与对应变更
R015: 回滚保留方法默认不得被任何生产路径调用；除显式执行回滚外，禁止调用、复用或继续修改该方法
R016: 编码期间只读取任务相关的源码、构建配置、运行配置、项目文档与用户或 CI 直接提供的错误文本；目录探测发现构建产物时须跳过，不得将产物内容作为实现依据
R017: 禁止打开、解析、反编译或提取任何编译与构建产物本体；默认排除 `target/`、`build/`、`dist/`、`out/`、`bin/`、`.gradle/`、`.next/`、`.nuxt/`、`.cache/`、`.turbo/`、`coverage/`、`node_modules/` 及其中内容，以及 `*.class`、`*.jar`、`*.war`、`*.ear`、`*.dll`、`*.exe`、`*.pdb`、`*.nupkg`、`*.o`、`*.obj`、`*.so`、`*.dylib`、`*.a`、`*.lib`、`*.pyc`、`*.pyo`；构建目录内的文本报告、生成源码和清单同样不得读取
R018: R019–R025 仅适用于修改已有业务功能且会改变服务方法直接入参/出参、Web 请求响应或外部可观察行为的任务；新增无旧契约的全新功能、恢复原行为的缺陷修复及不改变外部行为的内部重构不触发兼容流程
R019: 发现兼容风险时须在写代码前确认业务处于开发未上线还是已上线状态并提示用户选择开发流程；状态不明或用户未选择时禁止修改相关代码
R020: 开发未上线阶段须提示用户选择“兼容演进”或“本阶段不处理兼容”；选择不处理兼容后可在本次授权范围内直接调整契约和旧逻辑，但变更计划与结果须明确不提供新旧版本兼容
R021: 已上线业务须提示用户选择“兼容增量”“版本并行”或“直接替换”；默认推荐兼容增量，直接替换仅在用户确认调用方迁移完成并接受风险后执行
R022: 选择兼容增量时，已有 Web 接口保持 URL、HTTP 方法、鉴权、Content-Type、body 形状、响应包装及既有字段不变；请求只新增有旧行为默认值的可选字段，响应只新增字段
R023: 选择兼容增量时，对象包裹请求的新入参加入原对象并保持可选；标量、集合或非对象请求不得直接改为对象包裹或增加同级直参；服务方法直接参数列表或返回类型变化须保留旧签名并通过重载、新方法或适配器承接
R024: 选择版本并行时须新增版本化 URL、方法或 DTO，保留旧接口、旧签名及其生产逻辑；仍承接旧调用方的逻辑不得改为 `ForRollback`，仅用于恢复且不承接生产流量的旧实现按 R014–R015 处理
R025: 选择直接替换或开发未上线阶段明确不处理兼容时，可在授权范围内替换契约并移除旧生产入口，但旧核心实现仍须按 R014–R015 保留为 `ForRollback`；删除源码须另行获得用户明确授权

## 工作流

```
Step 0: 确认任务为写码（否则路由到其他技能）
Step 1: 读 project-spec.md 的项目约定、关键目录及相关外部引用，并仅在 R016–R017 允许范围内核对本仓源码与现有契约；业务功能修改须盘点现有入口、调用方、请求响应结构与旧行为
Step 2: 若存在兼容风险，提示用户确认开发未上线/已上线状态并选择 R020–R021 流程；输出含选择结果的变更计划 → 用户授权（R030）→ 列任务清单（R007，可豁免时声明）
Step 3: 实现代码，遵守 project-spec；优先用新方法承载变化并由原入口插入调用，核心逻辑改造按 R014–R015 保留旧实现，业务功能兼容按用户选择执行 R022–R025；发现新的关键目录或明确外部引用时轻量补充记录
Step 4: 完成文件逻辑自查并输出变更摘要；验证方式仅按用户当次要求与项目现有能力决定，不在技能中预定义脚本命令
```
