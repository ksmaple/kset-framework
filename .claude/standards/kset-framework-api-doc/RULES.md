# kset-framework-api-doc

> 执行约束以 [项目规则](../../rules/kset-framework-project-rules.md) 为准；必要时参考 [project-spec.md](../kset-framework-coder/references/project-spec.md) 中的项目事实与已确认差异。本规范不得覆盖或放宽项目规则。

## 触发条件

**启用**：当前任务命中规范 `kset-framework-api-doc` 的适用范围时读取；适用于按模块、接口或本次变更生成、更新、核对接口文档。

**不启用**：设计或修改接口契约与业务代码、定位接口缺陷属于其他角色。

## 核心规则

R000: 本规范仅在 kset-framework（proj=kset-framework）所属项目仓库及其工作树使用，跨项目任务须使用目标项目自己的规则与规范
R001: 默认只读取本次接口入口、参数与响应类型、实际异常码定义以及必要的业务调用代码；定义关键词时按需读取本次相关需求或功能设计；旧版接口代码与当前实现的对比须使用项目已确认的正式线上主分支（可为 `master`、`main` 或项目自定义分支）上有发布或部署证据的提交，在本次任务首次固定分支名及完整 Git SHA，同一任务后续迭代沿用该 SHA；仅在主分支开发的项目还须确认目标环境实际使用的正式发布版本及其与提交的对应关系，分支 HEAD 领先已发布版本时取已发布提交；无法确认分支或已发布提交，或单主分支项目无法确认正式发布版本与提交的对应关系时，将旧版差异标为待确认，不得以功能分支内先前修改替代；源码不能确认的接口事实才按需参考 project-spec 或用户明确提供的信息
R002: 新生成或未确认的接口文档，其接口名、路径、请求方式、Content-Type、参数位置与组织、返回 JSON、异常返回码与说明以本次实现为依据；已确认文档按 R029 保护，无法确认的内容标为“待确认”，禁止猜测或为生成文档修改接口实现
R003: 仅记录用户指定范围内的接口；未指定范围时以本次相关改动或明确模块为范围，仍无法确定时先列出可识别入口供用户选择
R004: 后端项目记录实际对外暴露的接口；前端或客户端项目只记录本仓实际调用的接口及已知契约，不把调用代码推断成服务端完整实现
R005: 默认按 `references/api-doc-format.md` 输出 Markdown 到 `.claude/design/api/{scope}.md`，其中 scope 为本次功能的稳定小写 kebab-case 名称；已确认文档受众时按 R027 使用受众后缀，写入前按项目规则 R140 核对现有文件归属和目标项目；用户明确指定现有目录或格式时按其要求；成稿只用一个一级标题，标题后注明文档受众与适用 Web 端，依次给出关键词定义、接口汇总、调用与逻辑链、从 1 连续编号的逐接口二级标题及必要的公共说明，使用 Mermaid 时序图、表格和带 `json` 语言标记的代码块，并删除占位内容与 HTML 注释
R006: 接口汇总后用 `mermaid` 代码块中的 `sequenceDiagram` 展示本次接口的调用与逻辑链；每张图须在图前标题及图内注明对应功能或场景，并标明调用方、实际参与方、请求及响应；只画可从实现确认的节点，链路不同时分别绘制；每个接口标题注明“新增接口”或“旧接口”，基线不足以判定时标“待确认”，并依次列出接口用途、路径、请求方式、请求类型、参数位置与组织、参数、返回 JSON、字段说明及异常返回码与对应说明；无参数时写“无”
R007: 参数表只保留参数名或字段路径、类型、必填性及必要说明；返回字段只保留字段路径与说明；异常返回码须标明码类型与所在位置，区分 HTTP 状态码和响应体业务 `errCode`，数值相同时仍分别记录，不得将 HTTP 400 当作响应体业务错误码；按实际实现填写，已核实没有异常码时写“无”，无法确认时写“待确认”，不为默认值或鉴权单设栏目
R008: 返回 JSON 须匹配本次实现的实际结构并可解析；非空对象和数组使用 2 空格缩进的多行格式，嵌套结构展开，不得使用紧凑单行格式；空对象、空数组、标量及 `null` 保持合法 JSON 原样；样例值须脱敏，不得将真实密钥、令牌、个人数据或环境配置值写入文档
R009: 仅在用户明确要求 OpenAPI/Swagger 时处理该格式；使用结构化解析与序列化，禁止用字符串拼接生成 YAML 或 JSON
R010: 文档生成只读取任务相关源码、配置、项目文档及用户直接提供的契约信息；禁止读取、解析或提取构建产物、生成源码、构建目录报告或运行日志
R011: 默认只做静态核对，不启动服务、调用真实接口、编译、测试、打包或部署；用户另行明确要求的运行验证须遵守项目规则的对应授权边界
R012: 更新已有 API 接口文档时只修改本次接口对应内容及相关汇总行、时序图和公共说明，保留其他接口正文和人工维护内容；已有文档混含客户端与管理平台接口且本次范围未覆盖全部接口时，按 R027 仅为本次接口生成或更新对应受众文档，保留原混合文档并在交付结果中列为待迁移；仅在已确定范围覆盖原文档全部接口且依据足以核对时，才将全部接口及人工维护说明按受众迁入对应文档，归属不明的内容保留原文并标为待确认，迁移完成的混合文档不得继续作为成稿；新增接口优先追加，插入或删除接口时仅调整必要的标题序号；以请求方式加路径识别路由，依据 R001 的对比基线判定新增或旧接口，旧接口单列本次新增、修改或删除的请求与返回字段，说明类型、必填性、默认行为等变化及影响，未变字段不重复列入；缺少可靠基线时标为“待确认”，不得猜测差异
R013: 输出前核对文档受众、适用 Web 端与接口归属一致，客户端和管理平台文档分别成稿，同一路由的分端契约差异未被合并，接口汇总与各接口章节一致、序号连续、新旧标记及旧接口字段变化有依据，时序图的功能或场景名称与实际调用一致，路径、方式、请求类型、参数位置与组织、参数、返回 JSON、异常返回码类型、所在位置与说明一致；校验 JSON 示例可解析，非空对象或数组为多行缩进格式；有待确认项时简短列明
R014: 修改文档前按 `.claude/rules/kset-framework-project-rules.md` R070a–R070o 与 R106 分类，并核对任务 worktree 或项目明确指定的主分支；提交与推送遵守该规则 R088–R089
R015: 多步骤任务须按 `.claude/rules/kset-framework-project-rules.md` R053–R054、R056–R057 完成验收与阻塞恢复
R016: 多个接口共用且已确认的说明集中放在文末“公共说明”，按主题分节并逐条列出适用接口与约定；没有公共说明时删除该节，禁止将不同约定压成单行
R017: 文档开头的“接口汇总”须按每个接口契约一行列明业务场景、适用端、请求方式与路径、用途及章节编号；同一路由的分端契约有差异时分别列行，并与文档受众、时序图和接口正文对应
R018: 整理整份文档时须识别可跨接口复用的请求与响应、鉴权、字段格式、状态与业务动作、分页、重试及新旧接口关系，仅汇总有依据且实际存在的主题；接口特有约束仍写在对应接口节，不重复堆放在公共说明
R019: 公共说明中的状态值等有限枚举须用表格，状态迁移或处理顺序用有序列表，默认值、单位和时间格式逐项列明，重试与结果确认独立列出步骤；已确认的例外紧邻相关约定，不将不同主题压成单行
R020: 整理接口约定时若发现与项目规则、项目规范或 project-spec 的约束冲突，须按 `.claude/rules/kset-framework-project-rules.md` R101–R104 核实适用范围与权威位置，未核实前不得改写契约结论
R021: 开始前须确定本次接口、模块、变更或契约基线及明确排除项；范围不明且会影响文档结论时按 R003 请用户选择
R022: 按已确定范围遍历实际入口、调用方与必要的被调用方、请求和响应类型、异常码、相关配置、调用链及旧接口对比基线；逐接口核对汇总、图和公共说明，记录未覆盖处及原因，发现差异后仍须完成范围内检查
R023: 范围内核对完成后须一次性交付完整文档及核对结果，列出覆盖接口、可定位依据、全部有证据的差异、未覆盖处与待确认项；中途可报告覆盖进度，不得把先发现的几项作为最终结论
R024: 默认接口文档属于项目规则 R106 的规范产物，Git 状态由项目决定；用户指定 `docs/` 等正式交付路径时按项目正常版本管理，不得因文件由本规范生成就扩大 Git 忽略范围
R025: 成稿前须按项目规则 R111 核对接口涉及的需求与功能设计关键词，在接口汇总前列出术语、定义、适用场景与设计依据；同词不同义须列明区别，缺少设计依据的定义标为待确认，字段业务含义沿用权威契约而不重新定义
R026: 生成文档前须依据可定位的接口路由、鉴权、调用方或项目约定判定每个接口面向客户端还是管理平台；归属无法确认且影响分文档时按 R003 确认范围，不得仅凭名称猜测
R027: 同一范围同时包含客户端和管理平台接口时须分别生成独立文档，不得混写；已确认受众的默认文件名分别为 `{scope}-client.md` 与 `{scope}-admin.md`，仅涉及一类时只生成对应文档，用户指定路径时仍须保持两类内容分离
R028: 存在不同 Web 端接口时须在文档头、接口汇总与逐接口章节说明具体适用端；同一路由在不同端的请求、鉴权、响应或异常行为有差异时分别记录对应契约，契约一致的共享接口列明全部适用端；无法从实现或项目约定确认的端标为“待确认”，不得将不同 Web 端笼统写成“Web”
R029: 用户已确认或正式发布且可定位版本的接口文档须保留其既定契约；实现与文档不一致时先报告差异，不得据实现自行覆盖原文。仅在用户已确认特定接口优化及其契约变化后，按本次确认范围更新对应内容并保留其他接口与人工维护说明
R030: 逐接口核对实际 Content-Type、表单独立字段、字符串 `payload` 内部结构或 JSON Body 形状；无业务参数时仍记录请求类型要求，同一路由不得把表单与 JSON Body 合并为一套兼容入参，按已确认版本并行的不同接口分别记录

## 工作流

```
Step 0: 按 R021、R026–R029 确认接口范围、受众、适用 Web 端与已确认文档基线，按 R014 核对输出分类及任务 worktree 或项目指定主分支
Step 1: 按 R022、R030 遍历范围内接口及关联处；定位变更前代码版本或当时有效契约，按请求方式加路径定位路由，核对适用端的请求编码与契约差异并梳理调用链、字段变化和跨接口共性
Step 2: 按 R027 将客户端与管理平台接口分别成稿，先按 R025 定义关键词，再按场景及 R028 的适用端汇总接口，用标明功能或场景的 Mermaid 时序图描述调用链；按序号为每个接口独立成节，填写 R030 的请求类型、参数位置与组织、格式化返回 JSON、旧接口字段变化及异常返回码；跨接口约定按主题整理为公共说明
Step 3: 静态核对各文档受众、适用 Web 端、接口汇总、接口事实、请求编码、时序图名称、公共说明与 JSON 语法和排版；按 R023 核对范围覆盖并交付完整文档，输出位置、未覆盖处与待确认项
```
