# kset-framework-coder

> 执行约束以 [项目规则](../../rules/kset-framework-project-rules.md) 为准；项目事实与已确认差异见 [project-spec.md](../../../docs/overview/design/project-spec.md)。本规范不得覆盖或放宽项目规则。


| 项    | 值                 |
| ---- | ----------------- |
| proj | `kset-framework`          |
| 类型   | **backend** |


## 触发条件

**启用**：当前任务命中规范 `kset-framework-coder` 的适用范围时读取；适用于本仓的项目内技术设计、功能实现、业务源码与数据结构变更等研发任务。

**不启用**：仅整理现有代码逻辑或设计业务需求与验收条件；编译/测试失败修错属于 fixer 职责；项目 AI 协作初始化使用 `kset-util-project-init`。

## 核心规则

涉及数据库结构、SQL 或索引时，先读 [数据库与 SQL 规则](references/sql-rules.md)（R085–R100c、R105–R126、R129–R134、R294–R298）。
涉及业务日志、异常日志或日志检索时，先读 [日志规则](references/log-rules.md)（R141–R166）。

R000: 本规范仅在 kset-framework（proj=kset-framework）所属项目仓库及其工作树使用，跨项目任务须使用目标项目自己的规则与规范
R001: 先读 project-spec.md，再对照本仓源码与现有契约
R002: 执行约束以项目规则为准；项目事实与已确认差异以 project-spec 为准，未登记事项优先沿用本仓现有做法；冲突时先核实并修正低优先级内容
R003: 项目内设计与业务代码实现只使用本规范，不依赖未生成的平台公共规范
R004: 新模块的架构、API、数据、时间格式及关键目录约定须先写入 project-spec
R005: 禁止把平台仓库外绝对路径或外部引用作为未确认的可执行依赖
R006: project-spec 与存量实现不足以确定方案时须先向用户确认
R007: 本规范默认验收标准为文件逻辑完成与静态自查
R008: 编写类名、方法名、API 操作名及入参/出参字段时须简单易懂，优先业务人员可理解的日常用语，避免晦涩缩写
R009: 改码前须先输出变更计划并获用户授权，禁止未经确认直接改文件
R009a: 用户对完整变更计划或任务清单整体明确授权后，授权范围内全部已确定步骤视为已获执行授权，无须逐步重复确认
R009b: 已获整体授权的确定步骤须按依赖顺序连续执行
R010: 本规范仅以文件逻辑完成与静态自查作为默认验证，不因项目已有能力自动执行命令
R011: 任务涉及外部文档、外部项目或跨仓文件时须先读取 project-spec 外部引用记录，并仅补充名称、位置、用途与关联目录
R012: 外部引用记录禁止复制外部正文或写入凭据、令牌和敏感查询参数
R013: 修改已有功能且无适用扩展点时，须优先将新增或变化逻辑实现为职责单一的新方法，并在原入口方法的适当位置插入调用；禁止在原方法体内持续堆叠新逻辑，已有适用扩展点时按 R235 接入
R014: 原方法本身属于核心逻辑且无法仅插入调用时，可按 R235 的边界与授权要求直接修改原方法；变更前须记录可定位的基线 Git ref 与受影响入口
R015: 不得为回滚而在源码中复制、保留不承接生产流量的旧实现；回滚须按功能变更记录中的 Git ref 恢复必要代码
R016: 编码期间只读取任务相关的源码、构建配置、运行配置、项目文档与用户或 CI 直接提供的错误文本；目录探测发现构建产物时须跳过，不得将产物内容作为实现依据
R017: 编码与静态核对期间禁止打开、解析、反编译或提取任何编译与构建产物本体；默认排除 `target/`、`build/`、`dist/`、`out/`、`bin/`、`.gradle/`、`.next/`、`.nuxt/`、`.cache/`、`.turbo/`、`coverage/`、`node_modules/` 及其中内容，以及 `*.class`、`*.jar`、`*.war`、`*.ear`、`*.dll`、`*.exe`、`*.pdb`、`*.nupkg`、`*.o`、`*.obj`、`*.so`、`*.dylib`、`*.a`、`*.lib`、`*.pyc`、`*.pyo`；构建目录内的文本报告、生成源码和清单同样不得读取
R018: R019–R025 仅适用于修改已有业务功能且会改变服务方法直接入参/出参、Web 请求响应或外部可观察行为的任务；新增无旧契约的全新功能、恢复原行为的缺陷修复及不改变外部行为的内部重构不触发兼容流程
R019: 发现兼容风险时须在写代码前依据发布、部署、标签、生产调用、调用方迁移和功能变更记录自动判定开发未上线或已上线；证据缺失或冲突时才提示用户确认，禁止仅凭源码存在或分支名称判定
R020: 开发未上线阶段须提示用户选择“兼容演进”或“本阶段不处理兼容”；选择不处理兼容后可在本次授权范围内直接调整契约和旧逻辑，但变更计划与结果须明确不提供既有契约兼容
R021: 已上线业务须提示用户选择“兼容增量”“版本并行”或“直接替换”；默认推荐兼容增量，直接替换仅在用户确认调用方迁移完成并接受风险后执行
R022: 选择兼容增量时，已有 Web 接口保持 URL、HTTP 方法、鉴权、Content-Type、body 形状、响应包装及既有字段不变；请求只新增有旧行为默认值的可选字段，响应只新增字段
R023: 选择兼容增量时，对象包裹请求的新入参加入原对象并保持可选；标量、集合或非对象请求不得直接改为对象包裹或增加同级直参；服务方法直接参数列表或返回类型变化须保留旧签名并通过重载、新方法或适配器承接
R024: 选择版本并行时须新增版本化 URL、方法或 DTO，保留旧接口、旧签名及其生产逻辑；仍承接旧调用方的逻辑须保持可调用
R025: 选择直接替换或开发未上线阶段明确不处理兼容时，可在授权范围内替换契约并移除旧生产入口及不再使用的旧实现；须核对调用方迁移、引用关系与回滚来源，已暴露的 RPC 接口仍按 R209 分阶段退役
R026: Java/Dubbo 项目中，服务暴露实现类及其 RPC 入口方法保持无事务，不得使用 `@Transactional`、`TransactionTemplate`、`PlatformTransactionManager` 或等价事务代理；发起其他 RPC 前须结束本地事务，调用方与被调用方的本地事务互不包含，避免事务代理改变服务导出类型
R027: RPC 入口需要本服务数据原子写入时，先核对单条原子写或唯一约束是否足够；确需且按项目规则 R078 获授权的多语句事务，须委托项目实际事务机制下的内部公共方法完成最小本地事务。Java/Spring 项目须确认事务经 Spring 代理生效，不依赖同类自调用；事务方法内不得调用远程 RPC，跨服务结果按 R067 核验和恢复。Dubbo 暴露类仅作无事务编排
R028: 本规范的文件修改范围遵守项目规则 R001；项目运行验收由适用角色和独立授权处理
R029: 测试执行遵守项目规则 R002、R046；本规范不运行测试
R030: 项目运行与启动遵守项目规则 R003、R041；本规范不启动运行进程
R031: 编译验证遵守项目规则 R004–R006、R038–R040；本规范仅在获当前对话授权后执行最小 compile-only 编译
R032: 实现配置、字典、元数据或常见查询时按项目规则 R007 评估缓存，并核对 project-spec 与源码中的现有缓存能力
R033: 缓存候选的适用条件遵守项目规则 R008
R034: 仅进程内使用、数据量有界且不要求跨节点一致的数据可使用项目现有本地缓存方式，并须设置最大容量与过期策略
R035: 跨节点共享或要求多实例一致视图的数据按项目规则 R010 使用现有分布式缓存方式
R036: 配置中心或配置框架已提供缓存与动态刷新时须复用其读取和刷新机制，禁止叠加不可失效的二级缓存
R037: 缓存 Key 须包含影响结果的全部查询维度以及适用的租户、用户、语言或版本隔离信息
R038: 缓存落地前须明确 TTL、更新或删除时机、并发回源、空值策略与权威数据源回退路径
R039: 强一致或实时数据的缓存例外须满足项目规则 R011 的全部条件
R040: 项目无适用缓存能力时，新增依赖或基础设施须遵守项目规则 R012
R041: 同一功能再次调优或替换实现时，历史调优信息只读取已有 `docs/{module}/changes/{feature-key}.md`，不查 Git 历史与其他功能记录；本次范围内的源码与契约盘点仍按 R170 执行；获授权后、改码前建立或更新本轮基线，实施中继续同步实际结果
R042: 功能变更记录须遵循 references/feature-change-record-spec.md，并在写代码前记录当前入口、被替代实现、本轮相关文件、上线状态判定快照、基线 Git ref、回滚目标与回滚来源
R043: 功能变更记录的内容边界遵守项目规则 R014–R015，并按 references/feature-change-record-spec.md 记录符号、职责与状态
R044: 每轮调优须分配稳定 change-id，并将新实现标为 active；旧实现按是否承接生产流量及实际清理结果记录状态
R045: 仍承接旧接口或旧调用方的兼容实现按项目规则 R016 标为 active-compatible，不得按过期实现清理
R046: 功能变更记录须关联旧实现的文件、符号、受影响入口和可定位的基线 Git ref
R047: 删除旧实现的生产调用与兼容迁移条件遵守项目规则 R017
R048: 清理本次替换范围外的历史过期实现时，计划内容与授权遵守项目规则 R018
R049: 回滚目标与恢复来源遵守项目规则 R019，完成后同步更新功能变更记录中的实现状态
R050: 缺少历史记录时只允许根据当前源码建立基线，禁止虚构旧 change-id、调用关系或 Git ref；无可定位 Git ref 时须标记回滚不可用
R051: 有副作用的请求、任务、消费或共享数据修改按项目规则 R020 识别重复、并发及中断风险
R052: 先区分同一业务操作重试与新的有效触发；发奖、资金或积分权益变化、不可逆外部副作用及用户接口的一次性提交若重复生效会造成业务错误，须以稳定业务单号、条件写或唯一约束保证只生效一次；仅需识别同键异参时保存参数指纹并返回幂等冲突，榜单积分累加按 R183 的逐次计分或周榜去重契约处理
R053: 适用请求幂等时，幂等结果须与核心业务结果在同一本地事务提交，或由数据库唯一约束与条件写保证只有一个执行者生效
R054: 请求正确性的防重边界遵守项目规则 R023，进程内集合和 `synchronized` 均不能作为唯一依据
R055: 远程结果未知时按项目规则 R024 核验原业务单号，确认未执行后才允许复用该单号重试
R056: 自动重试只适用于明确的瞬时错误，并须设置次数上限、指数退避与随机抖动；业务拒绝、幂等冲突与未知结果禁止盲目重试
R057: 请求链路须贯穿 traceId、适用的业务单号、幂等键、租户或用户上下文，日志不得记录敏感原值
R058: 定时任务按项目规则 R025 核对实例数、调度器互斥保证、周期重叠和业务并行口径；多实例按单执行者设计且已有适用 Redis 锁时默认按 R288–R289 加锁，单机布尔值和静态字段不能作为唯一依据
R059: 全局单例定时任务按项目规则 R026 优先复用现有分布式调度互斥或适用 Redis 锁；无适用能力时按项目规则 R037 核对替代方案及新增基础设施授权
R060: 面向业务数据的定时任务按实际并发范围选择任务、分片或记录级保障；允许多实例分片处理时不以长时间全局锁串行整批，同一记录并发会造成业务错误时仍须原子抢占或条件写保护结果
R061: 数据库租约遵守项目规则 R028；递增版本作为 fencing token 使用时，提交前须以持久化条件拒绝过期旧持有者
R062: 任务重复执行会使价值操作重复生效时，分片执行可用任务名、调度窗口与分片键标识抢占范围；分片内每条价值操作仍须以稳定业务键及适用操作码建立独立防重标识，周期性价值操作按业务口径纳入调度窗口，并用唯一约束或条件写保证只生效一次，分片执行标识不得替代逐条防重。无分片任务按实际业务操作粒度确定执行标识；周期投影或对账覆盖须防止旧结果覆盖新结果，不把任务抢占等同于事件去重
R063: 批量任务遵守项目规则 R029，按稳定唯一键排序，并在 HTTP、MQ、文件 IO 期间结束事务与锁
R064: 定时任务单条失败按业务契约决定停止或继续；允许其他项独立完成时在现有边界记录原异常及必要业务标识后继续，不默认新增重试状态。核心结果要求可靠完成且选用内建逐项重试时，才记录重试次数、下次执行时间与最近错误并设置处置上限；已有外部对账补发能力时核验其结果
R065: 按项目规则 R030 确定每类业务事实的权威源与所有者；缓存、搜索索引、统计表和只读副本仅作派生视图
R066: 同一数据库内的不变量须由本地事务、条件更新、版本号或唯一约束保证，禁止以“先查询再写入”作为并发正确性依据
R067: 跨服务正常路径须明确权威事实和适用幂等处理；低概率基础设施故障的残留流程或数据问题按项目规则 R032 在设计中说明人工定位、处理责任与结果核验。已确认要求系统自动修复时先复用现有对账补发能力，仍不足才按具体风险设计可靠投递或补偿；可偶发失败的附属动作沿用既有处置，禁止用跨服务长事务或分布式大事务包住远程调用
R068: 写入确认、幂等判定与补偿核验遵守项目规则 R033，读取主库或具备一致性保证的权威接口
R069: 数据修复与对账实现须具备稳定范围、幂等执行、断点续跑、变更审计与停止条件，禁止无条件覆盖权威事实，禁止一次性全量修改
R070: 发现重复、脏数据或多源冲突时须保留差异证据并按明确规则处置，禁止静默取第一条、最后一条或任意来源覆盖
R071: 多租户查询与分布式标识的隔离维度遵守项目规则 R035
R072: 调度、租约、过期和对账的时钟及时区遵守项目规则 R036
R073: 跨节点业务主键、业务单号与任务执行标识须复用项目现有全局唯一生成方式，禁止使用单机内存计数或裸时间戳拼接
R074: 完成静态自查时须分别记录请求幂等适用判断、任务抢占、数据权威源、一致性、重试与恢复策略；不适用项须说明原因
R075: 分布式实现的现有能力复用与新增基础设施授权遵守项目规则 R037，并以 project-spec 和源码确认能力边界
R076: 代码研发阶段的前端构建、发布与部署禁令遵守项目规则 R042
R077: 编译验证仅在项目规则 R039 授权的范围内执行最小 compile-only 编译
R078: 编译验证授权的排除项遵守项目规则 R040
R079: 指定环境的部署授权及必要操作遵守项目规则 R043；部署执行由 `kset-framework-environment` 承担
R080: 部署范围与测试、开发服务器边界遵守项目规则 R044
R081: 编译、运行与部署的授权来源遵守项目规则 R046，任务或工具参数不构成授权
R082: 上线状态自动判定须优先采用可定位到功能版本的生产发布或部署证据，其次采用版本标签与发布映射、生产调用、调用方迁移及既有功能变更记录
R083: 每次上线状态判定须记录判定时间、结果、证据、证据来源、基线 Git ref 与当时入口、接口契约、调用方、迁移状态和实现状态
R084: 上线状态记录是对应 change-id 的时点快照，后续上线或再次迭代须新增记录，禁止回写历史状态；证据不足或冲突时须询问用户
R101: 任务结束与阻塞恢复须遵循 `.claude/rules/kset-framework-project-rules.md` R053–R054、R056–R057
R102: 开始设计、编码或调整配置前须读取 project-spec 的「构建与基础设施兼容基线」，确认任务涉及的 Java、构建工具、数据库、框架、中间件、客户端及依赖管理版本

Step 4.10: 涉及查询入口、写入流程或事务边界时按 R118–R124a、R297–R298 核对纯查询无显式事务、写事务内有界条件查询与正确锁范围、回滚和有界死锁重试，以及必要读写与幂等结果原子提交
Step 4.11: 按 R238 从受影响入口静态核对正常、拒绝、重复、部分执行、异常或超时及异步终态的适用结果；核对权威事实、对外反馈与恢复去向一致，记录待确认和未覆盖处
Step 4.12: 按 R239 核对日志无重复、敏感信息或吞异常，附属异常未引入无依据的补偿与状态，主业务失败未被日志伪装成成功；低概率基础设施故障的人工处理信息可定位、可核验
Step 4.12a: 按 R272 核对业务触发时间归属、结算延后窗口及正常丢弃的消息与周期日志；核心结果不得按附属消息特例丢弃
Step 4.13: 按 R240 核对新增处理中态具有人工介入或强制等待依据，领取状态对应客户端真实操作，未持久化可推导状态或暴露后端重试细节；发放事实可按业务键对账，缺记录未直接判定失败，补发不重复生效且核心结果可核验
Step 4.14: 按 R241、R281 核对新增业务路径的组件与模式适配性、是否复用公开 API，业务复杂逻辑未沉入 Redis 或组件适配层；缺口方案须有差异、是否采用、用户授权和适配层范围记录
Step 4.15: 代码实现及相关脚本完成后，按 R246 使用文末提示词核对本次适用的强制编码规范；先修正已授权范围内的问题，再完成交付门禁
Step 4.16: 按 R247–R248、R273 核对幂等与一致性改动是否属于本次已确认需求或明确授权的优化范围；确需短时 Redis 防重时核对原子占位、TTL、Key 隔离、重复结果与失效行为，未授权的专项改造不实施
Step 4.16a: 事件消息按 R273 核对同一链路仅一次短时占位及去重命中、处理失败、结果未知、Redis 故障和 TTL 到期路径；周榜及适用的其他附属计数按 R183 核对单条 `SET key value NX EX/PX` 同时设置标记与 TTL、标记先于累加及异常保留，明确逐次计分不误去重；独立消费者与核心操作各守不变量
Step 4.17: 按 R249–R271、R299 核对本次改动涉及的集合、空值、资源、异常、并发、长整型定点计算与溢出、状态判断与流转、SQL、转换、分层及 Web/RPC 契约类型；不适用项记录依据，不以静态核对代替测试
Step 4.17a: 涉及文件导入导出或中文乱码时按 R300–R301 核对源字节、字符集、字段映射、输出格式与回读结果；不得将静态检查称为跨软件兼容验证
Step 4.18: 涉及 Redis 时按 R197、R274–R281 核对业务代码只调用公共工具或适配接口、脚本符合项目规则 R165–R167、无模糊查询、所有仍存在 Key 的有限 TTL、适用的原子过期、周期性 Key 补设窗口、失败告警与有界修复、仅业务允许时清理及结果核验；核对 String、Hash、List、Set、ZSet 选型及不适用时的用户决策，榜单 member、score、排序及同分口径，Set 的无序和容量边界；达到或预计达到大 Key 阈值时核对切片设计与迁移，热点和分片按实际指标核对读写成本、稳定路由及原子性，无法保持已确认不变量时报告设计阻塞
Step 4.19: 按 R291 核对本次被替换的旧代码、静态引用、动态调用及兼容入口；清理确认无用的旧实现并更新适用的功能变更记录，历史过期实现按 R018 处理；按项目规则 R018、R018a–R018b 排查本次涉及目录的干净程度，核对废弃文档、目录与相关产物的归属、替代迁移、引用和恢复依据，定向删除后复查残留、断链与 Git 状态，报告保留及未核实项
Step 4.20: 按 R290 核对已有相关文档并同步受最终代码改动影响的内容；契约差异按 R199 处理，交付时列出未确认的待同步项
Step 4.20a: 已有需求设计的实现状态受影响时按 R302 更新关联位置与代码状态，核对测试和发布状态未被代码改动误写为已完成
