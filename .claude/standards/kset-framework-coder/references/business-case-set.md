# 业务用例集模板

本模板供 `kset-framework-coder` 在业务实现前按需梳理场景，并用于实现后的文件逻辑自查。它不是可执行测试脚本，也不构成运行测试授权。简单变更可不选用；仅在用户要求、跨入口或多状态变化等场景需要逐项核对时选用。

## 逻辑闭环说明与场景

逻辑闭环是让本次受影响的入口、权威事实、调用方可观察结果与必要后续处理相互一致。成功须由实际完成的业务结果支撑；拒绝、失败、部分执行或结果未知也可为明确的终点或进入已有恢复路径。异步受理只表示已接收任务，不表示最终成功。按 coder R236–R238 核对适用路径；简单查询或无副作用变更不需要额外状态机、补偿表或重试。以下场景只作选择参考，具体口径以需求、契约与项目事实为准。

| 场景 | 正常路径的闭环 | 拒绝、失败或结果未知 | 再次触发与边界 |
| --- | --- | --- | --- |
| 同步写入 | 权威写入确认后返回与实际状态一致的结果 | 参数或业务拒绝返回明确原因；写入失败不报告成功 | 按同一业务操作标识核对重复请求，不把重试误当新操作 |
| 异步受理 | 入口返回受理状态与任务标识；最终处理结果按已确认契约可核验 | 处理失败保留可定位结果，并进入适用的重试、对账或人工处理 | 入队或发送成功不等于任务完成；重复消费按业务口径处理 |
| 普通事件短时去重 | 需要拦截同一逻辑消息短时重投且已有 Redis 时，在单一消费链路选一个入口边界，按消费方、租户、稳定消息标识原子占位并设置有限 TTL；内部步骤复用结果 | 明确失败仅释放本次占位并沿用现有有界重试；Redis 故障按既有策略处理，命中去重不报告业务完成；核对内部没有重复占位 | TTL 到期后仍可能重复或遗漏；独立消费者和核心结果各守业务不变量，逐次计分不去重 |
| 外部结果未知 | 原业务单号关联本地事实与外部权威结果，确认后更新状态 | 超时先查询权威结果；仍未知时保持待核验状态或已有复查入口 | 未确认原操作未生效前不换单号盲目重做 |
| 批量处理 | 每项结果可归入成功、拒绝或失败，批次汇总与逐项事实一致 | 单项失败按契约隔离、续跑或停止，不能把部分成功报为全成功 | 重跑只处理符合当前状态的项目，避免重复价值变化 |
| 周期重建 | 以完整权威事实和有效水位形成可核验的新结果 | 来源不完整或旧水位时跳过覆盖，并保留已有结果 | 可安全重建的派生结果按周期与水位纠偏，不机械增加逐项补偿 |
| 迟到的周期附属消息 | 按业务触发时间归属；结算预留有界延后窗口，窗口内原周期仍开放时按原周期处理 | 上周期强制结束或超窗不可再写且允许遗漏时，确认丢弃并记录消息标识、业务时间、周期及原因的普通日志，不作为异常或默认人工补发 | 不按消费时间改入新周期或自动重开；核心价值和明确必达结果仍核验恢复 |
| 普通通知 | 核心业务事实确认后按现有渠道尽力发送 | 允许遗漏时记录必要日志或指标，通知失败不回滚核心事实 | 未有明确必达承诺时不为通知增加状态机或无限重试 |
| 附属或内部异常 | 主业务事实和对外结果保持正确，系统继续稳定运行 | 在现有处理边界记录一次可定位的原异常，保持既有传播和返回语义 | 不为推测的异常中断新增补偿表、状态机或复杂事务 |
| 主业务异常 | 权威事实、对外反馈与业务契约一致 | 核心部分写入或结果未知时先核验事实；低概率基础设施故障无自动修复承诺时明确暂由人工处理及定位、责任和核验方式，已确认承诺时才设计自动恢复 | 再次触发须核对重复生效与漏执行风险，不误报成功 |
| 状态类需求 | 客户端明确需要领取等操作时按真实业务条件表达，可推导结果不重复保存 | 仅为后端重试设想的阶段不暴露为客户端业务状态 | 只有人工介入或强制中断等待且现有事实不足时新增处理中态；真实生命周期仍保留 |
| 发放事实对账 | 资格或触发事实与实际发放结果分别记录在所属权威表，按原业务键关联 | 处理窗口后缺少结果记录时先查发放方权威结果；确认未发放才幂等补发 | 普通奖励及补发不为对账另设中间态，不能凭缺记录断言发放失败或成功 |
| 后端异步补发 | 主请求返回与已确认事实一致的结果，补发由独立后端入口处理 | 按原业务键先核验权威结果，确认未完成后有界补发 | 不由客户端盲目重试，也不把入队或重试当成已完成 |
| 只读查询 | 返回值、筛选范围、权限与实际读取事实一致 | 无权限、参数错误或依赖失败按现有契约返回 | 不因“闭环”要求新增持久化状态或副作用 |

## 示例：业务榜单

以下用例归纳 coder R182–R188 的 Redis 榜单实现口径；独立逐次累加计数可借用单命令原子增量、定时快照及适用的补偿边界，但按 coder R184 使用逐用户计数 Key，不照搬 LB-01 的共享 ZSet 结构。选用时按实际功能保留适用行；补偿、通知和周榜事件去重均为可选能力，未启用时删除对应行。周期、计分增量、同步频率、前 N 名阈值、同分排序和通知变化类型由具体业务确认。普通计分不因可选补偿预先维护最后触发时间或版本。

| ID | 类型 | 触发与前置条件 | 输入或关键数据 | 预期业务结果与副作用 | 依据或待确认项 |
| --- | --- | --- | --- | --- | --- |
| LB-01 | 正常 | 榜单计分入口收到一次触发 | 周期、租户、用户、计分增量 | 按周期及租户定位共享 ZSet Key，以用户 ID 为 member，单命令原子累加其分数；本次触发不写 SQL 或补偿元数据 | coder R182、R184；计分口径待业务确认 |
| LB-02 | 再次触发 | 榜单按逐次生效契约再次收到有效触发，包括相同信息再次到达 | 与上次相同或新的计分信息 | 每次有效触发均再次累加积分，不据相同字段自动去重 | coder R183；与可选周榜去重口径二选一 |
| LB-02a | 周榜去重（可选） | 契约要求在标记有效期内抑制稳定事件重复计分，且接受占标记后异常漏计 | 项目、租户、周周期、操作、主体、稳定事件 ID、计分增量 | 优先复用入口去重结果；否则用同一条 Redis `SET key value NX EX/PX` 命令设置覆盖周榜及迟到重投窗口的标记与 TTL，不拆成 `SETNX` 后单独 `EXPIRE`；仅首次确认占标记成功后累加，命中标记跳过；Redis 故障或标记过期后仍可能重计或漏计 | coder R183；事件标识、TTL 与漏计容忍度待业务确认 |
| LB-02b | 占标记后异常（可选） | 周榜去重标记已成功设置，累加失败或结果未知 | 稳定事件 ID、标记 Key、原异常 | 保留标记并记录异常，不释放标记重试累加；本次分值可能遗漏，不能声称两步原子或恰好一次 | coder R183；按业务契约结束处理 |
| LB-03 | 定时 | 周期 SQL 同步任务到期，Redis 已有榜单分数 | 周期、快照水位、有界批次 | 按批读取 Redis 并保存 SQL 榜单快照；重叠任务的旧水位不能覆盖新结果 | coder R185；同步频率待业务确认 |
| LB-03a | 查询 | 业务需要返回长期留存的榜单数据，SQL 快照满足目标周期与完整性要求 | 周期、快照水位、查询范围 | 优先从 SQL 快照有界返回并标明数据时效，不作为实时榜单结果；快照不满足要求时按查询契约处理 | coder R182、R185；留存周期与时效要求待业务确认 |
| LB-04 | 补偿停止或跳过（可选） | 非 SQL 来源事实不完整，或现有能力不能在单个无事务原子操作中比较并覆盖 Redis 分数 | 事实完整性、当前分数或水位、可用原子能力 | 不执行自动补偿覆盖；普通原子计分继续，SQL 不参与补偿 | coder R186–R187；缺口及后续处理待确认 |
| LB-05 | 补偿覆盖（可选） | 非 SQL 来源事实完整，且已证明现有单命令能力可安全比较并覆盖；正负计分时比较依据能排除分数回原值后的新触发 | 完整非 SQL 事实、重算所依据的分数或可靠水位 | 原子核对当前值未变后条件覆盖；条件成立只覆盖 Redis，SQL 由下一次独立定时任务同步，否则跳过，不以分步读写覆盖 | coder R186–R187；比较依据与原子能力待项目确认 |
| LB-06 | 周期通知（可选） | Redis 中本周期与上周期的固定快照均可用 | Redis 两期快照、本周期前 N 名、变化类型 | 仅向符合变化条件的本周期前 N 名用户通知，不读 SQL，也不在每次榜单触发时通知 | coder R188；N、同分排序及入榜变化口径待业务确认 |
| LB-07 | 故障与恢复 | Redis 故障，或同步间隔内 Redis 数据丢失 | 故障时间、最近快照水位、业务可接受偏差 | 实时路径按契约返回失败或不可用，不以 SQL 快照冒充实时值；说明可能的重计或漏计，不为跨 Redis 与 SQL 故障时绝对无偏差增加双写或逐事件持久去重 | coder R182、R188；核心价值结果另按其权威事实核验 |

## 示例：配置草稿与发布

适用于运营或管理端编辑配置。默认将未发布草稿保存在前端本地，并与后台已发布配置区分；只有用户提交发布时才上传后台。发布记录、操作日志及缓存策略须结合项目现有能力确定。涉及密钥等敏感内容、多人协作或跨设备续编时，先确认本地保存是否适用，不套用默认口径。

| ID | 类型 | 触发与前置条件 | 输入或关键数据 | 预期业务结果与副作用 | 依据或待确认项 |
| --- | --- | --- | --- | --- | --- |
| CFG-01 | 草稿 | 有编辑权限的用户修改配置，尚未提交发布 | 配置标识、编辑内容、已发布版本 | 前端本地保存草稿；后台已发布配置、变更记录和运行缓存均不改变 | 本次需求；本地存储方式及保存范围待项目确认 |
| CFG-02 | 草稿恢复 | 用户重新打开编辑页，本地存在该配置草稿 | 本地草稿、后台已发布版本 | 明确展示本地草稿及其与已发布版本的关系；用户可继续编辑或放弃草稿，未发布内容不进入对外配置读取 | 本次需求；跨设备与多人编辑口径待业务确认 |
| CFG-03 | 发布 | 用户确认发布且有权限，草稿校验通过 | 配置标识、草稿内容、操作人、所依据的已发布版本 | 前端提交后台；后台校验并持久化新发布版本，记录变更内容与操作审计，成功后返回新版本；前端收到成功确认后清理对应本地草稿 | 本次需求；审计字段、版本冲突口径待项目确认 |
| CFG-04 | 发布拒绝 | 参数或业务校验失败，或发布期间已发布版本发生冲突 | 草稿内容、当前发布版本、拒绝原因 | 后台不更新已发布配置和运行缓存；返回可识别原因，前端保留草稿供修正或重新核对 | 配置变更模板；冲突处理口径待业务确认 |
| CFG-05 | 配置读取 | 业务或展示入口读取已发布配置，缓存适用且命中 | 配置标识、租户或环境、版本等影响结果的维度 | 返回已发布版本的缓存数据；本地草稿不可被其他用户或业务读取 | cache K012–K020；缓存候选与隔离维度待项目确认 |
| CFG-06 | 缓存回源 | 缓存未命中、过期或不可用 | 配置标识、权威存储、TTL 与回源策略 | 从后台权威数据源读取已发布配置；适用时回填缓存，缓存故障不改变发布事实 | cache K023–K025；TTL、空值与并发回源待项目确认 |
| CFG-07 | 发布后失效 | 新版本发布已持久化 | 新旧版本、受影响缓存 Key | 在后台提交成功后按项目机制删除或刷新受影响缓存；失效失败按既有恢复策略处理，不把旧缓存或前端草稿当作权威配置 | cache K004、K023–K024；短时陈旧容忍度待业务确认 |

填写时删除不适用项和占位行。预期结果以已确认需求、现有契约与项目事实为依据；缺少依据时标记待确认，不臆造业务规则。用例集可放入本轮变更计划或按用户指定位置交付；默认不另建项目文件，不自动编写或运行测试。
