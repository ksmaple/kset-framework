# 业务流程通用归类与组合

本文件供 `kset-framework-coder` 在项目流程目录未覆盖时使用。它只提供分析与组合方法，不预置业务种类、主流程数量、状态表或代码实现。先核对本项目契约、源码、project-spec 与本次需求；有依据的项目专属流程优先。

## 整体流程

```text
触发适配 → 核对前置事实 → 执行最小主干 → 确认一个主要结果 → 返回真实反馈
                                   ├─ [条件扩展：契约要求时]
                                   └─ 后续主流程：以前段已确认结果触发
失败、部分完成、超时、结果未知或事实差异 → 核验原权威事实 → 续做、纠偏或人工处理
```

逐段写明触发、结果、事实所有者和失败去向。受理、投递、调度或消费成功不等于业务完成；组合不构成单一事务，各段的重复、重试与交付保证分别判断。

## 最小流程归类

| 层级 | 判定 | 必须记录 |
| --- | --- | --- |
| 独立主流程 | 脱离渠道和调度仍有独立可观察结果及所有者 | 触发与前置事实、权威事实及所有者、必选主干、条件分支、主要结果与真实反馈、重复与并发口径、失败去向及恢复入口 |
| 主干条件分支 | 与主流程共享结果和所有者，仅合法条件或处理方式不同 | 分支条件、拒绝路径和各路径真实结果 |
| 触发或执行适配 | 只改变入口、时机、批次或投递方式 | 输入标识、进入条件、适配失败与主结果确认方式 |
| 条件扩展 | 主结果不依赖它；具体契约或已确认风险要求时才接入 | 触发条件、输入事实、时机、扩展结果与所有者、失败对主结果的影响 |
| 后续主流程 | 另有独立结果或事实所有者 | 前段已确认结果、后段触发事实及各自恢复入口 |
| 恢复流程 | 失败、部分完成、超时、未知或事实差异后进入 | 原业务标识、权威事实、续做或人工处理条件及最终核验 |

先从完整场景识别结果与所有者，再剥离扩展和适配。只有触发、主要结果、事实所有者及重复和失败语义相同，且差异仅是条件时，才合并为同一主流程的分支。相同代码形状、业务标识或调用链不足以证明结果相同；不为达到固定模板数量而合并。

## 可选能力

| 能力 | 何时接入 | 结果与失败边界 |
| --- | --- | --- |
| 草稿续填 | 确需恢复未提交内容；普通编辑优先核对前端本地保存，跨设备、协作或留存要求再确定服务端归属 | 草稿只供恢复编辑；正式提交属于对应主流程，仍核对权限与版本，失败保留草稿；草稿有独立可查询结果时升为主流程 |
| 通知 | 契约要求告知，输入为已确认的触发事实 | 发送失败不改写原结果；通知本身是业务目标时升为主流程，交付保证按契约确定 |
| 缓存刷新 | 读路径实际依赖缓存且权威事实已变化 | 失效或刷新失败按查询契约处理，不代替权威结果 |
| 独立修改审计 | 追溯、合规或契约要求记录独立变更流水 | 与结果对象的必要版本字段、诊断日志区分；失败是否阻断由契约决定 |
| 导出 | 明确要求文件交付 | 单独核对范围、权限、水位和文件结果；失败不自动否定原结果 |
| 周期视图 | 明确要求固定周期、水位或历史查询 | 作为附属结果时按条件接入；它本身是主要承诺时升为主流程 |

可选只表示不对所有项目预设；具体场景的契约已要求时，该项就是必做项。未触发的扩展从场景流程中删除，不留空步骤。

## 适配与恢复

| 适配或恢复条件 | 处理边界 |
| --- | --- |
| HTTP、事件、定时或批量 | 仅在进入同一业务动作时归适配；逐项结果仍由各自权威事实确认 |
| 主动发起 | 契约要求用户执行明确动作时核对发起权限与资格；仅改变进入方式时归适配，动作本身有独立可查询结果时升为主流程 |
| 周期迟到消息 | 仅在普通事件有业务归属周期且可能跨期到达时确定时间来源、延后窗口、超窗处置和结果保障等级 |
| 事件短时去重 | 仅在普通事件契约要求时选择一个消费入口边界，明确标识、TTL、失败与未知处置；不替代主业务幂等 |
| 定时批量处理 | 按窗口有界推进，逐项核验；多实例互斥、分片和失败游标只在对应执行契约要求时接入 |
| 核验与恢复 | 沿用原业务键查询权威事实；确认仍未完成后才按原入口续做或交人工，不将未知直接判为失败 |

首次正常外部结果确认若产生新结果，按主流程判断；失败或未知后再查原结果属于恢复。适配的短时占位、任务锁和批次汇总都不构成最终业务结果。

## 保障强度选择

对每项写入或副作用按失败后果、业务承诺、并发冲突和可恢复性选择保护；只实现能覆盖已知风险的最小原子保护和恢复流程。权威价值及须逐次生效的变化守住本地不变量，可重建的附属结果按完整来源和水位恢复，普通附属动作按已确认的交付要求处理。

## 状态需求与后端异步补发

状态可由事实或时间推导时不重复保存；客户端确需业务操作时保留真实操作条件；仅为后端恢复设想的阶段不进入客户端状态；人工介入或强制等待且现有事实不足时才增加最小处理中态；真实业务生命周期按契约保留必要状态。恢复按原业务键及允许的处理窗口跨表对账，先查询原操作结果，再决定是否续做；不为普通恢复另造统一状态表。

存储、计数、缓存、消息和调度的执行细则按项目规则与角色规范核对；本文件只用于识别它们归属的业务结果、适配和恢复边界。

## 组合记录

```text
结果 A（所有者 A 已确认）→ 流程 B（所有者 B 确认结果 B）
  [扩展 C：触发条件、输入事实、结果、失败去向]
  [恢复 D：失败或结果未知时核验的原事实]
```

交付时列出主流程清单、合并或降级依据、条件扩展、典型组合、未覆盖范围和待确认项。静态盘点不代表测试、运行验收或线上使用证明；流程描述复用不要求公共基类、统一状态表、通用补偿框架或跨服务事务。
