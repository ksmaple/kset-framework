# kset-framework-fixer

> 执行约束以 [项目规则](../../rules/kset-framework-project-rules.md) 为准；项目事实与已确认差异见 [project-spec.md](../../../docs/overview/design/project-spec.md)。本规范不得覆盖或放宽项目规则。

## 触发条件

**启用**：当前任务命中规范 `kset-framework-fixer` 的适用范围时读取；适用于代码审查、编译或测试失败、Lint 告警和运行时缺陷，保持已有代码风格。

**不启用**：新功能开发或项目内设计属于 coder 职责。

## 核心规则

R000: 本规范仅在 kset-framework（proj=kset-framework）所属项目仓库及其工作树使用，跨项目任务须使用目标项目自己的规则与规范

R001: 先读 project-spec 并核对本仓失败上下文，保持与 `kset-framework-coder` 风格一致

R002: 最小变更，禁止借机大面积重构

R003: 修复默认验收标准为文件逻辑完成与静态自查

R004: 输出含根因、策略、影响范围；不确定时列出待确认项

R005: 命名/API 类问题以 project-spec 与本仓现有契约为准

R006: 文件逻辑交付默认不受编译或测试阻塞；验证方式仅按用户当次要求与项目现有能力决定
R007: 代码审查优先报告功能、回归、数据与契约缺陷；密钥、令牌、凭据问题仅在本次审查范围直接涉及且证据明确时报告，通常降低优先级，已确认的严重泄露风险按实际影响报告
R008: 缺陷涉及外部文档、外部项目或跨仓文件时须核对 project-spec 中的轻量引用记录，禁止把未确认的外部位置当作修复依据
R009: 定位缺陷只读取 project-spec、任务相关源码、构建配置、运行配置、项目文档及用户或 CI 直接提供的错误文本；不得为复现或补全上下文读取构建产物文件
R010: 缺陷定位与静态核对期间禁止打开、解析、反编译或提取任何编译与构建产物本体；默认排除 `target/`、`build/`、`dist/`、`out/`、`bin/`、`.gradle/`、`.next/`、`.nuxt/`、`.cache/`、`.turbo/`、`coverage/`、`node_modules/` 及其中内容，以及 `*.class`、`*.jar`、`*.war`、`*.ear`、`*.dll`、`*.exe`、`*.pdb`、`*.nupkg`、`*.o`、`*.obj`、`*.so`、`*.dylib`、`*.a`、`*.lib`、`*.pyc`、`*.pyo`；构建目录内的文本报告、生成源码和清单同样不得读取
R011: 修复与测试代码处理阶段默认不执行测试，仅当用户在当前对话明确要求运行测试时方可执行最小测试目标
R012: 修复与测试代码处理阶段默认禁止编译，仅当用户在当前对话明确要求编译验证时方可执行最小 compile-only 编译
R013: 测试授权不包含编译，编译授权不包含测试、打包、安装、启动、预览、发布或部署
R014: 修复与测试代码处理阶段默认禁止启动或运行应用、服务、容器、开发服务器与 H5 预览服务器
R015: 修复与测试代码处理阶段默认禁止 H5 或前端生产构建、打包、上传、发布与部署
R016: 用户当前对话明确要求部署并指定目标环境时，部署执行交由 `kset-framework-environment`，本规范仅交付修复结果与部署所需的已核实信息
R017: 修复、测试或编译授权不扩展为部署授权；部署范围按项目规则 R043–R044、R129–R131 由 `kset-framework-environment` 核对
R018: 测试授权只包含最小测试目标及其进程内测试上下文；触发未授权编译、独立应用或服务启动、预览或部署时须停止并说明
R019: `runCompile`、`runTests`、任务描述、CI、配置文件、工具参数与项目默认流程均不得替代用户对编译、测试、运行或部署的当前对话授权
R020: 用户对完整修复计划或任务清单整体明确授权后，授权范围内全部已确定步骤视为已获执行授权，无须逐步重复确认
R021: 已获整体授权的确定步骤须按依赖顺序连续执行
R023: 任务结束与阻塞恢复须遵循 `.claude/rules/kset-framework-project-rules.md` R053–R054、R056–R057
R024: 定位和修复前须读取 project-spec 的「构建与基础设施兼容基线」，确认故障模块实际使用的 Java、构建工具、数据库、框架、中间件、客户端及依赖管理版本
R025: 修复须保持目标模块基线版本兼容；同一组件按模块锁定多个版本时沿用故障模块版本，受父 POM/BOM 管理的依赖禁止脱离依赖管理自行指定版本
R026: 未经用户当前对话明确授权，禁止把升级、降级、替换组件或混用基线外版本作为修复手段，也禁止使用基线版本不支持的语法、API、SQL、配置项和协议能力
R027: 修改文件前须遵循 `.claude/rules/kset-framework-project-rules.md` R070a–R070o 与 R106，核对任务分支及 worktree 或项目明确指定的主分支，并核对文件分类；提交或推送须核对该规则 R088–R089
R028: 当前工作树缺少项目规范、project-spec 或项目规则时须先完成该项目的初始化
R029: 代码审查依次检查业务逻辑、业务模型边界、高并发正确性、过度设计；发现的严重级别仍按实际影响判定
R030: 审查分级为 P0（已证实的资金或核心数据错误、不可逆损失）、P1（可复现的主要流程或并发错误）、P2（有证据的跨业务耦合或冗余设计）、P3（非缺陷建议，默认不报告）
R031: 每项发现须给出本次审查范围内的位置、触发条件、后果与最小修正；无明确证据的假设风险不得驱动大范围改造
R032: 充值订单表默认不得因币商功能增加币商专属字段；币商上下级快照等由币商侧关联表承载，按业务边界通过订单 ID 或订单号关联；用户明确允许且 project-spec 记录共表理由时可例外
R033: 高并发审查聚焦幂等、条件写或唯一约束、权威结果与有界重试；只对可证实的重复发放、漏发或错误状态提出修正
R034: 补发优先复用一次主流程、现有订单状态与有界定时任务；失败记录异常并提示处理，外部结果未知先核对再幂等补发，禁止仅凭事务风险猜测新增草稿表、独立状态表或多套流程
R035: 修复涉及项目规则、项目规范或 project-spec 中的约束时须按 `.claude/rules/kset-framework-project-rules.md` R101–R104 核对归属、重复、语义冲突和引用
R036: 代码审查开始前须依据用户目标确定审查对象、时间或变更基线、涉及的业务流程与明确排除项；范围不明且会影响结论时须先澄清
R037: 按已确定范围检查改动及其直接关联的调用方、被调用方、数据读写、配置与契约，并核对 R029 的检查项；记录未覆盖处及原因，发现问题后仍须完成范围内检查
R038: 范围内检查完成后一次性整理完整审查报告，按实际影响列出有证据的发现、覆盖范围、未覆盖项与待核实事项；中途进度可说明覆盖状态，不得把先发现的几项作为最终报告
R039: 修复同一业务功能的日志时须沿用项目规则 R108 与现有功能关键词、操作、阶段、结果及业务标识字段；修复前后保持检索口径一致，必要变更须检查同功能关联日志，不得为统一格式增加无诊断价值的日志或泄露敏感值
R040: 修复前后须按项目规则 R110 核对本次依赖边及其直接与传递路径能否返回依赖方；依赖公共 API 时分别定位 API 与实现模块并检查实现层反向路径。发现环时记录可复现路径并消除本次新增的环边；无关存量环只报告，不扩大修复范围
R041: 修复代码须精简冗余分支、临时变量与重复包装；简单逻辑在语义清晰且符合项目格式规范时尽量一行表达，复杂逻辑保持易读的分行结构，不得为压缩行数牺牲正确性、可读性或可调试性
R042: 修复跨模块业务前后按项目规则 R116 核对事实所有者、规则决策位置与适用契约；按缺陷责任在所属模块修正业务规则，在调用方修正自身编排或结果适配，不得为绕过原问题复制对方规则或直接维护对方业务结果
R043: 修复 RPC 与事务交叉问题时按项目规则 R078、R078a、R078c 核对调用方和暴露层均未在本地事务内执行远程 RPC；本服务原子读写先核对单条原子写或约束是否足够，确需新增或扩大事务时取得授权并由项目实际事务机制下的内部公共方法完成。Java/Spring 项目须确认代理入口生效，禁止把跨服务调用纳入事务或依赖同类自调用触发事务
R044: 修复业务流程结构时，主方法默认按真实执行顺序展示关键步骤，列表处理交由职责明确的子方法；可独立的后续阶段平级处理列表或批次结果，不在入口循环内混合多个阶段。逐项依赖、短路、流式处理、内存或事务边界需要局部循环时保留并说明理由
R045: 修复嵌套分支时优先用前置校验、提前返回与清晰分支降低理解成本；必要的条件层级可保留，不得为形式拆出空转发层，或改变条件优先级、执行顺序、异常传播、事务范围及遍历成本
R046: 修复批量流程中的远端 N+1 调用时，优先复用已有批量、分页或合并接口，并按服务端容量与超时约束有界分批；逐项调用承担顺序、失败隔离、限流或内存边界时保留并说明依据，不得为减少次数改变 RPC/HTTP 契约、幂等结果或事务范围
R047: 代码审查或故障排查须以已确定范围及直接关联处为每轮边界排查默认5轮；已覆盖既定范围且本轮确认无新问题时可不满5轮提前停止，满5轮仍有新问题须继续排查
R048: 只读审查仅报告发现；修错任务排查结束后，单文件不超过10行、可逆、低风险且不改变跨模块流程、接口、数据、依赖或业务契约的简单问题须直接修复并报告结果，其余改动须先说明方案，未获明确授权时询问用户，获授权后方可实施
R049: 异常路径审查与修复须按项目规则 R135 核对主业务事实、用户可见结果、系统稳定性和原有异常语义；仅影响附属或内部处理且核心结果正确时，优先在现有处理边界记录一次可定位的原异常日志，不为推测的异常中断新增复杂一致性、状态或补偿。已证实的正常路径缺陷仍须最小必要修复；低概率基础设施故障的残留问题按项目规则 R032 明确人工处理，已确认自动修复承诺才增加系统恢复
R050: 修复状态类业务逻辑时按项目规则 R136 核对新增处理中态是否确需人工介入或强制中断等待且现有事实不足；领取等客户端真实操作及已确认的业务状态须保留，可由事实推导的状态不重复持久化。普通发放和补发可按原业务键跨表核对时，不为修复新增奖励中间态；缺少结果记录先核验发放方权威结果，确认未发放后按既有幂等能力恢复，不让客户端状态承载补发编排
R051: 跨项目缺陷须按项目规则 R138 读取已确认依赖项目的相关规则、说明和公开契约，核对实际依赖版本与故障调用链；对方规则只用于定位责任与兼容边界，不能替代本项目规则。修复或修正规则按项目规则 R139 归属到各自项目，不得在本项目复制对方约束或越界修改对方实现
R052: 审查结论和修复摘要默认在对话中交付；用户要求独立报告文件时按项目规则 R141 写入 `docs/{module}/reports/code-review/`，保留范围、依据和待核实项，不把未执行的修复或测试写成已完成结果
R053: 幂等与跨服务一致性按项目规则 R143 控制范围；未获当前对话明确授权时，不对已有功能启动专项排查、优化或新增持久防重、对账、补偿机制。本次普通一次性写请求仅在业务契约要求短时拦截时按项目规则 R144 选择适用防重；其余仅处理本次已确认的缺陷范围并保持触及路径原有正确性，范围外已证实问题只报告证据与影响
R054: 审查或修复本次触及的代码时，按实际路径核对集合、空值、资源、异常、线程安全、数值、SQL 参数化及跨层转换；有限业务或流程状态的判断与流转须使用所属业务范围集中定义的枚举或具名静态常量，不得直接比较状态字符串字面量或魔法数字，持久化及传输状态码按既有契约在边界映射；确定业务结果及集合元素须使用具体类型，泛用 JSON 返回仅用于已确认且结构无法预先确定的可扩展或透传契约；涉及 Web/RPC 时核对已知字段由明确契约类型承载、DTO 不嵌套 Entity，既有接口变更按项目兼容规则处理
R055: 审查或修复 Redis 业务路径时按项目规则 R112、R150–R151、R165–R167 核对公共工具与适配层归属、脚本必要性及 Key、Cluster 槽、成本、失败口径、事务与模糊查询禁令、完整 Key、所有仍存在 Key 的有限 TTL、适用的原子过期、周期性 Key 补设窗口、失败告警与有界修复、仅业务允许时清理及结果核验、覆盖写保留 TTL、序列化和有界操作；锁组件内部脚本同样核对适用边界，业务层不得直接提交任意脚本。多命令执行、管道及锁不构成整体原子操作；没有方案能保持已确认不变量时报告阻塞及替代方案，不改成非原子读写
R056: 审查 Redis 性能问题时按项目规则 R152–R154 核对单 Key 大小与成员数、访问频率、延迟、内存及批量边界；达到或预计达到大 Key 阈值时须按 R152 设计切片键、单片上限、路由、迁移切换和原子性边界，同时保持有界读写与清理；热点和分片须有证据及稳定路由，不得为优化延迟引入无界聚合、Key 扫描或破坏原子性
R057: 审查本次触及的消息消费链路时按项目规则 R149 定位入口短时去重与后续调用；同一逻辑消息已在该链路完成去重时，指出内部服务或业务步骤重复占位和第二套去重状态，修复时复用入口处理结果。周榜及其他非必达附属计数仅在契约明确按稳定事件去重、允许漏计并确认异常后保留标记时，核对单条 Redis `SET key value NX EX/PX` 同时设置标记与 TTL、标记先于累加及异常后保留，不套用普通事件失败释放占位的处理；其余普通消息仍核对失败释放。独立消费者及核心价值操作的业务幂等须分别核对，不因移除重复占位而删除必要的不变量保护
R058: 审查本次触及的 Redis 数据结构时按项目规则 R155 核对 String、Hash、Set、ZSet、List 的访问语义和容量边界；榜单核对 member 稳定性、score 精度、排序及同分规则、有界读取和逐次原子增量，Set 核对无序与有界成员操作。发现数据结构不适用时仅修复本次已授权范围，其他存量问题记录证据和影响
R059: 审查或修复本次触及的 Redis、数据库、MQ、HTTP 客户端、调度器或设计模式时按项目规则 R156 核对组件场景与公开 API 是否适用；Redis 中的多分支业务逻辑、跨组件编排和异常恢复须归还所属服务，不在通用适配层扩展。缺少可直接调用的适用能力时先报告差异、备选方案、影响与授权状态；未获方案授权或能力不足时停止该方案，不以复杂封装掩盖问题，已获本次计划授权的不重复请求
R060: 修复本次触及的源码须遵循项目已有格式化配置、Lint 规则及同类文件风格；无明确约定时统一同一文件的缩进、括号、引号与分隔符，按职责分段留空行，按语言惯例留空白，长参数、条件和链式调用按语义分行并对齐，不以手工空格排版或在一行挤入多个独立语句
R061: 有适用的项目格式化工具时按其配置格式化本次触及的文件并核对差异；超出本次修复范围的格式化改动须排除，不因美化改写无关文件或改变程序语义
R062: 修复本次触及的方法若混合可独立命名的业务阶段、交错的条件与副作用，或不同失败处理难以从入口核对，按职责拆出有实际处理内容的步骤；主方法保留关键决策与执行顺序，并核对参数和结果传递、调用层级、异常、事务及执行成本，不为压缩行数增加空转发层或过长调用链
R063: 修复本次触及范围内的重复实现时，仅在业务语义、输入输出、副作用、职责归属与变更原因一致时复用已有方法或提取职责明确的共用步骤；不一致时保留各自实现，不因代码形状相似而合并；提取后核对各调用方的条件优先级、顺序、异常与事务语义，不扩展到无关模块
R064: 审查或修复本次触及的草稿功能时，核对本地保存适用性、用户和对象隔离、存储失败提示、恢复版本冲突、异步保存顺序及提交后清理；提交失败须保留可恢复内容，服务端仍校验正式提交。确需服务端草稿时核对归属、权限、版本、过期和删除，不因普通续填缺陷新增草稿表
R065: 审查或修复本次触及的多实例定时任务时，核对调度互斥和并行口径；按单执行者设计且已有适用 Redis 锁时，核对锁范围跨冲突窗口、拿不到锁自动跳过、Redis 故障不误判为竞争、有限租期与续租或失锁停止、仅持有者原子释放，以及跳过和过期后的业务恢复。业务价值结果仍单独防重，不为刻意分片并行的任务加全局长锁
R066: 每次代码修复后按项目规则 R158 核对本次功能已有的相关文档；实际内容受影响时，同次更新对应段落、示例和索引，核对文档与最终修复一致。已确认或正式发布的契约按项目规则 R119 保护，未获确认的差异记录为待同步项
R067: 修复替换旧逻辑后按项目规则 R017 核对本次范围内被替换的旧代码及实际调用入口；确认不再使用的代码须同次清理并更新适用的功能变更记录，历史过期实现按 R018 另行授权；清理后再按 R066 同步受影响文档
R068: 审查或修复 Redis Cluster 路径时按项目规则 R160–R167 核对 DB 0、集群客户端、同槽多 Key、脚本显式 Key 与逐节点缓存、故障重试、管理命令禁令及在线路径有界性；写入结果未知不盲目重试，发现命令或路由缺口时记录触发路径和影响，在本次授权范围内修复
R069: 审查或修复 SQL 结构与查询时按项目规则 R168–R170 核对字段类型、定点小数的缩放单位与整数列、非空默认和回填、大字段访问、显式投影、隔离条件、有界分页、参数化及动态排序；索引疑似失效须以目标版本执行计划和实际数据分布定位原因，不仅凭 SQL 形状或索引存在下结论
R070: 审查或修复事务及死锁时按项目规则 R171–R172 核对事务内查询与索引、锁范围和顺序、隔离级别、异常回滚、数据库死锁证据及有界整事务重试；业务冲突、外部副作用和结果未知不得盲目重做
R071: 审查或修复本次触及的整数型业务数值时，核对内部字段、参数、返回值和计算中间值默认使用项目语言适用的长整型；较窄整数类型仅用于已确认契约、框架签名或集合索引等明确边界。核对实际值域、计算溢出及跨语言或传输精度，无法无损表示时在边界采用无损表示；保留已有契约，金额和小数按 R072 处理
R072: 审查或修复本次触及的金额及固定精度小数时，核对按已确认单位和小数位缩放为长整型后在底层存储、计算，输入校验精度、展示输出转换为字符串；乘除及跨精度运算核对缩放、舍入和中间值溢出。长整型无法无损承载时使用适用的精确数值类型并说明原因，既有接口及存储契约按兼容规则处理，不以浮点数往返金额
R073: 审查或修复文件导入导出及中文乱码时按项目规则 R173 从原始字节、声明编码、解析映射、展示到输出回读定位问题；核对格式、列与类型、错误反馈及兼容边界，不靠重复转码掩盖已损坏的数据，未运行的回读验证须标为未核实

## 工作流

```

Step 0: 确认任务为代码审查或修错（新功能 → kset-framework-coder）；修改文件时按 R027–R028 核对文件分类、任务工作树或项目指定主分支与本地 init 产物

Step 1: 读 project-spec 的项目约定、构建与基础设施兼容基线、关键目录及相关外部引用；审查时先按 R036 确定范围，修错时仅使用用户或 CI 直接提供的失败信息，并遵守 R009–R010 的读取边界

Step 1.1: 故障链路涉及已确认依赖项目时按 R051 核对对方规则入口、公开契约及当前依赖版本，标明各项目的责任与待核实差异
Step 2: 审查按 R037 遍历范围，修错时定位根因并拟定最小补丁；两类任务均按 R047 循环排查，审查发现再按 R029–R034 排序、定级并给出最小建议，多步骤修复按项目规则 R084 建立并更新任务清单

Step 2.1: 涉及异常路径时按 R049 核对主业务事实、对外结果、系统稳定性与原有日志，区分附属异常、正常路径缺陷及低概率基础设施故障的人工处理或已确认自动修复承诺

Step 2.2: 涉及状态或补发缺陷时按 R050 核对客户端契约、权威事实、可推导状态与后端异步恢复入口，定位多余状态或漏掉的核心结果核验
Step 2.3: 按 R053 确定幂等与一致性是否属于已确认缺陷范围或获授权优化；未授权时不开展既有功能专项排查或扩项改造
Step 2.4: 按 R054、R071–R072 仅核对本次触及路径的基础编码、整数与定点小数的类型、精度及溢出、状态判断与流转、业务返回值及 Web/RPC 类型风险，记录可定位的触发条件和影响
Step 2.4a: 涉及导入导出或中文乱码时按 R073 核对源字节、格式契约、字符集与错误发生的边界，区分格式错误和业务数据错误
Step 2.5: 涉及 SQL 结构、查询、索引或事务问题时按 R069–R070 核对实际方言、执行计划、数据分布、锁与死锁证据，区分已证实问题和待核实项

Step 3: 审查任务核对发现的证据、级别与范围覆盖情况，并按 R038 整理完整报告；修错任务按 R048 决定直接修复或先询问，修复后完成文件逻辑自查并按 R040 核对变更后的依赖路径及公共 API 实现模块的反向依赖，发现环时记录可复现路径和本次环边的处理结果；涉及跨模块业务时按 R042 核对规则与结果的归属，涉及 RPC 与事务时按 R043 核对事务边界及代理生效路径，涉及流程结构调整时按 R044–R046、R062–R063 核对主方法、批量阶段、远端调用次数、分支与原有语义；涉及 Redis 时按 R055–R056、R058–R059 核对适配层、脚本、模糊查询、数据结构选型与业务逻辑归属、大 Key、热点及分片，其他组件和模式按 R059 核对场景适配及授权，涉及消息消费时按 R057 核对入口与内部重复去重；测试与编译验证仅按 R011–R019 的独立用户授权执行，部署请求按 R016–R017 转交 `kset-framework-environment`，不在规范中预定义脚本命令

Step 3.1: 异常路径修复后按 R049 静态核对原异常仅在处理边界记录一次，未吞掉原异常、误报主业务成功或为低概率基础设施故障引入无依据的补偿流程；人工处理依据可定位

Step 3.2: 状态或补发修复后按 R050 核对合法业务状态仍可查询、客户端未承担后端恢复阶段，异步补发复用原业务键并有界结束
Step 3.3: 修复替换旧逻辑后按 R067 核对本次范围内的旧代码、静态引用、动态调用及兼容入口，清理确认无用的实现并更新适用的功能变更记录；按项目规则 R018、R018a–R018b 排查本次涉及目录的干净程度，核对废弃文档、目录与相关产物的归属、替代迁移、引用和恢复依据，定向删除后复查残留、断链与 Git 状态，报告保留及未核实项
Step 3.4: 按 R066 核对已有相关文档并同步受最终修复影响的内容；已确认契约的差异按项目规则 R119 处理
Step 3.5: SQL 修复后按 R069–R070 核对字段与查询结果、执行计划、事务回滚和并发语义，记录无法在当前环境验证的性能或死锁风险

Step 4: 通过项目规则 R053–R054、R056–R057 完成门禁后输出审查发现或修复摘要

```
