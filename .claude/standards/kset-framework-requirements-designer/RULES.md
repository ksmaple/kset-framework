# kset-framework-requirements-designer

> 执行约束以 [项目规则](../../rules/kset-framework-project-rules.md) 为准；项目事实与已确认差异见 [project-spec.md](../../../docs/overview/design/project-spec.md)。本规范不得覆盖或放宽项目规则。

## 触发条件

**启用**：当前任务命中规范 `kset-framework-requirements-designer` 的适用范围时读取，遵守项目规则 R134；用于梳理现有代码、调用链和业务流程，或设计新功能与现有功能调整。

**不启用**：仅依据产品目标、原始需求或原型编写产品侧 PRD，且不核对项目源码、现有行为或实现映射 → [项目 PRD 规范](../../standards/kset-framework-prd.md)；实现代码、设计技术契约或修改 project-spec → `kset-framework-coder`；缺陷定位与修复 → `kset-framework-fixer`；按实现整理接口文档 → `kset-framework-api-doc`。

## 核心规则

R000: 本规范仅在 kset-framework（proj=kset-framework）所属项目仓库及其工作树使用，跨项目任务须使用目标项目自己的规则与规范
R001: 开始前须读取 project-spec 中与本次主题相关的项目事实、术语、关键目录和外部引用记录
R002: 须依据用户指定范围、项目已有行为与已确认的业务约束区分事实、推断和待确认事项
R003: 须明确使用角色、现有用途或业务目标、触发条件、范围、主流程、例外流程和完成结果
R004: 须列出不在本次范围内的事项，避免把未确认的相邻功能写成需求
R005: 涉及状态、金额、库存、额度或其他数值变化时须写明前置条件、允许的变化、重复请求与失败后的业务结果
R006: 涉及跨角色、跨系统或定时处理时须写明责任方、触发时机、可见结果及异常处置
R007: 需求设计模式的验收条件须可观察、可判定，并覆盖主流程、关键边界和失败场景
R008: 缺少会改变说明范围或验收结果的信息时须向用户提出具体问题；未获答复的事项标为待确认，禁止猜测成已确认事实
R009: 不得把技术实现方案、数据表、接口字段或部署步骤当作用户已确认的业务需求
R010: 须按 references/requirements-format.md 将现状说明写入 `docs/{module}/reports/logic-{feature-key}.html`、需求设计写入 `docs/{module}/requirements/{feature-key}.html`；同一功能共用项目规则 R140 的稳定 `feature-key`，写入前核对现有文件归属；用户指定位置时遵从用户要求，交付格式仍为 HTML
R011: 更新已有说明文档时须保留已核实的现有行为；需求设计模式须另行标出本轮变化及其影响的验收条件
R012: 本规范只读取任务相关源码、配置、项目文档与用户提供的信息，禁止读取构建产物、生成源码或运行日志
R013: 本规范只做文档逻辑与项目事实静态核对，不修改业务源码或执行编译、测试、启动和部署
R014: 修改说明 HTML 前须按 `.claude/rules/kset-framework-project-rules.md` R070a–R070o 与 R106 分类，并核对任务 worktree 或项目明确指定的主分支；提交与推送遵守该规则 R088–R089
R015: 多步骤任务须按 `.claude/rules/kset-framework-project-rules.md` R053–R054、R056–R057 完成验收与阻塞恢复
R016: 生成前须核对目标项目的实际模块、包、接口、服务方法、数据库表与已有行为，不得用通用示例代替项目事实
R017: HTML 须在图下方写明适用的项目、模块与现有约定；需要调整的部分仅在需求设计模式列出
R018: HTML 须以项目分栏时序图为主视图，自上而下展示参与方交互与业务结果；需求设计的类图及适用的其他 UML、数据关系图在同页作为结构视图，并通过编号关联主流程
R019: 领域对象、类或组件的职责及关系须在相关主线节点说明中定位；需求设计涉及的类与类关系还须在设计类图中可见
R020: 相关说明框须标明负责的项目、模块、包及该包承担的执行逻辑
R021: 涉及持久化的节点须标明实际数据库与表名并区分读取和写入；绘制 SQL 表关系图时，相关表、业务键、约束及关系须与图中内容对应
R022: 无法从项目事实核实的项目、包、方法、表或行为须标为“待确认”
R023: 需求设计模式发现已有对应实现时须在图中定位现有流程与实现位置，并分别标注本次新增、修改、沿用或移除的内容
R024: 修改项须说明原有行为、本次行为及受影响的流程和验收条件
R025: 需求设计模式中需要落地的节点须分别标注已完成、进行中、未完成或不适用的状态
R026: 已完成节点须有可定位的实现位置与已满足的验收条件；仅有代码但未满足验收条件时不得标为已完成
R027: 进行中或未完成节点须说明剩余工作、受影响流程及待确认或阻塞事项
R028: HTML 须按主流程、异常与恢复、通信路径、数据流、并发控制、领域、项目与包及数据存储为同一张图提供筛选视图；变更状态仅在需求设计模式适用，评估建议在需求设计或用户明确要求评估时适用
R029: 单类别视图须保留必要的主流程节点和连线，避免说明框失去上下文
R030: 类别视图与对应说明框须使用稳定且可区分的浅色底色，并保留类别标题和图例
R031: 图中节点名称须精简为接口名、服务方法名或业务动作名，不展示类的全限定名
R032: 详细说明须通过悬浮与点击提供，触屏设备不得只依赖悬浮交互
R033: 图下方须完整列出现有行为、实现映射、注意事项、依赖及未核实事项；需求设计模式还须列出需求、变更清单与验收条件
R034: 图中节点与图下方对应说明须可相互定位
R035: 本规范交付物须为可独立打开的 HTML 文件；时序图与设计类图直接以 HTML 元素和 CSS 呈现，禁止使用 Mermaid、SVG/Canvas 画布、绘图编辑器或外部画图工具生成图形
R036: 输出前须检查完整视图与各筛选视图的文字、连线、颜色对比、遮挡及桌面和移动端交互
R037: Git 仓库中由本规范生成的详情页和需求主页面不因本地协作用途或 AI 来源自动忽略、取消跟踪或暂存；带 `kaka-requirements-designer:index` 标记仅用于识别页面归属，不改变 Git 状态。业务自定义页面与仓库 `.gitignore` 由项目自身维护
R038: 已被 Git 跟踪的说明 HTML 须报告其跟踪状态，不得仅凭本地过滤规则声称其不会被提交
R039: 开始时须按用户目标选择“现状说明”或“需求设计”模式，并在 HTML 顶部标明文档类型
R040: 现状说明模式须依据源码与已确认项目资料整理实际入口、调用顺序、分支、异常处理及结果，不要求存在新需求
R041: 现状说明模式须把可定位的类、方法、配置与数据读写映射到图中节点及图下说明
R042: 现状说明模式须为关键行为标注可定位的源码或项目文档依据
R043: 现状说明模式不得把代码中可见的路径推断为已在生产运行或已通过验收
R044: 现状说明模式不得生成未经用户提出的新增、修改或移除建议；用户明确要求评估时的优化建议按 R079 处理
R045: 现状说明模式无本次交付目标时须将变更类型与完成状态标为“不适用”，不得虚构验收条件
R046: 现状说明模式须逐节点区分代码可见、未发现实现与待核实，并注明依据，不能用交付完成状态代替现有实现判断
R047: 流程图中的实际入口、调用顺序、条件分支和异常路径须与可定位的现有实现逐项核对
R048: 需求设计调整既有流程时须让共用部分自上而下保持一条主线，仅在变化处引出对应版本路径
R049: 同层级且同一父节点的分支须尽量并列对齐，汇合节点与连线方向须清晰，避免布局暗示错误的执行先后
R050: 不同领域、项目包和数据库表须各自采用稳定可区分的颜色标识，同一实体在完整视图和筛选视图中保持一致
R051: 需求设计中新增、修改和移除的节点、连线及关联说明须分别用可区分且带文字标签的颜色边框或背景范围包裹
R052: 变更颜色须与领域、项目包、表的身份颜色并存，不得覆盖原有类别含义或仅靠颜色传达变更类型
R053: 旧版流程须标明项目已确认的正式线上主分支名称、发布或部署证据及本次任务首次固定的已发布提交完整 Git SHA；仅在主分支开发的项目还须标明目标环境实际使用的正式发布版本及其与提交的对应关系。新版流程标明本次任务结果或拟议状态；同一任务多轮迭代沿用该旧版 SHA
R054: 设计中的新路径须明确标为拟议行为
R055: 无法确认正式线上主分支、已发布提交或核实其行为，或仅在主分支开发的项目无法确认正式发布版本与提交的对应关系时，旧版流程须标为待确认，不得以分支 HEAD 或功能分支内先前修改补写旧版
R056: 跨项目或跨进程的连线须标明调用方向、通信方式及同步或异步关系，并区分 Web HTTP、直连 RPC、消息投递等实际路径
R057: 关键通信连线须关联可定位的接口、生产者、消费者或配置依据；拟议路径须标为设计方案
R058: 涉及并发写入、重复触发或竞态的关键节点须标明业务并发条件及现有或拟议的保护方式
R059: 只有已核实使用或方案明确拟议使用互斥锁的节点才显示带文字说明的小锁标识；无锁或无法核实的节点分别标明“无锁”或“待确认”
R060: 锁说明须关联业务键、锁范围、获取与释放时机及获取失败后的业务结果；无法核实的细节须标为待确认
R061: 唯一约束、条件更新、版本号和事务等非互斥锁保护须按实际机制标注，不得仅用锁图标代替
R062: 适用的异常路径须在同一张图中从触发节点连接到处置动作及最终业务结果，图下说明不得代替缺失的图上路径
R063: 异常节点须区分失败原因、自动重试或补偿、人工处理及失败后对调用方或用户可见的结果；现状说明须按已核实的实现标注自动恢复或人工处置，无法核实则标为待确认；需求设计涉及系统重启、服务发布、RPC 断联及 MySQL、Redis、MQ 等低概率基础设施故障时，未有已确认自动修复承诺的残留流程或数据问题须标注“暂由人工处理”，并写明业务键、定位依据、责任方、处理入口与结果核验；仅在已确认要求系统自动修复时设计新增自动恢复路径
R064: 图中信息须按业务结果影响、数据一致性风险及使用者关注度确定展示优先级
R065: 主流程和高影响异常须保持醒目的节点与连线，次要路径及技术细节须弱化但仍可点按查看和按编号定位
R066: 无法从现有实现核实的异常处置须在图上标为“待确认”，拟议处置须标为设计方案
R067: 关键业务数据须在同一张图中从来源经必要转换和跨边界传递追踪到权威落点及对外结果
R068: 数据流须沿现有流程节点和连线标明关键数据名及产生、读取、写入、投递或消费动作，避免复制一张平行流程图
R069: 关键数据流须用稳定编号关联图下来源、转换、落点与可定位依据，未知环节须标为待确认
R070: 复杂时序图及结构图须允许浏览器缩放、横向滚动及按编号定位，桌面与触屏均可辨认参与方、关系方向和图下说明
R071: 类别筛选与节点选中须保持可追踪的视图位置和编号对应关系，不得因切换筛选而丢失当前关注路径
R072: 默认视图须优先呈现主流程和高影响异常，次要数据与技术细节通过筛选或点按展开
R073: HTML 的图示与导航功能须在离线独立打开时可用，不依赖外部 CDN 或在线服务
R074: 需求设计须核对新旧流程、业务约束、接口与数据关系中的冲突，并说明双方依据及业务影响
R075: 优化建议须针对可定位的流程节点或连线说明现状问题、预期收益、代价或风险，不得把推测写成已证实缺陷
R076: 冲突与优化建议须以独立编号标记在同一张图的受影响节点、连线或片段上，并与图下评估说明双向定位
R077: 评估标记须区分“冲突”和“建议”及高低优先级，不得与新增、修改、移除的变更标记混淆
R078: 未获确认的建议须标为“待决策”，不得写成已确认需求或已完成实现
R079: 现状说明模式仅在用户明确要求评估时展示优化建议，且须与已核实的实际行为分开
R080: 未发现有依据的冲突或优化点时，图下评估结果须写“无”，不得为填充文档虚构问题
R081: 补充说明须关联图中编号，记录影响理解流程的前提、约束、假设和适用边界
R082: 对照新旧版本时，差异节点、连线和数据流须分别以 `OLD-`、`NEW-` 开头并各自编号
R083: 共用节点、连线和数据流须以 `SHARED-` 开头，不得借用版本专属编号
R084: 旧版与新版节点的沿用、替换、拆分、合并和移除关系须逐项映射，不得凭序号相同认定为同一动作
R085: 图、说明表、验收条件和定位链接须引用完整编号；更新已有 HTML 时须同步修改所有旧编号引用
R086: 修订文档时须保留已有编号，只为新增内容在所属编号类别后追加编号
R087: 每个共用动作须只画一个 `SHARED-` 节点，不得在版本分支重复绘制
R088: 版本分支须从发生变化的节点或连线切出，并标明版本与变化条件
R089: 版本分支与共用主线或另一分支后续行为相同时须汇入唯一的共用节点，不同时须分别连接实际结果
R090: 未变化的流程段须沿共用主线向下，不得为对齐版面添加空分支
R091: 需求设计涉及项目规则、项目规范或 project-spec 中的约束时须按 `.claude/rules/kset-framework-project-rules.md` R101–R104 核对归属、重复、语义冲突和适用例外；证据不足的冲突须标为待核实
R092: 不同模块之间存在调用、依赖或数据引用时，须为各模块使用稳定且可区分的身份色标，在引用连线两端标明来源与目标模块的对应色标，并在图例列出模块名称与颜色映射；箭头和文字仍须说明引用方向与关系类型，不得仅靠颜色表达
R093: 生成 HTML 时须以 `references/sequence-page.html` 为页面结构参考，直接编写参与方、按实际流程命名的阶段、按时间排序的消息行、适用的设计类图及图下说明；删去示例内容，不得把底稿占位或参考图片的业务内容当作项目事实交付
R094: 消息行须用 `data-from`、`data-to` 指向参与方顺序，以 HTML 文本标注编号、动作、通信方式和关键数据；方向与生命线由 CSS 呈现，类别筛选只改变可见行，不得改变业务时序
R095: 修改成稿 HTML 时须保持消息编号及图下锚点引用一致；图下依据、冲突、建议和验收条件不得因筛选或排版丢失
R096: 时序主视图须按实际项目划分栏位，同一项目内按模块列出参与方和生命线；跨项目、跨模块消息须从来源栏指向目标栏，时间顺序自上而下，不得仅凭版面位置推断执行顺序
R097: 每条关键交互须标明消息编号、动作或接口、同步/异步或读写关系；请求、响应、投递、消费、异常和补偿分别按实际先后落在对应时间位置，缺失的调用方或目标标为待确认
R098: 业务数据、状态或数值变化及额外说明须附着于对应节点或连线编号，在图上显示紧凑摘要，在图下记录完整来源、转换、落点、依据、前提与待确认项；结构图不得另造与主时序不一致的业务路径
R099: 增删参与方或消息行后须复核项目栏位、生命线、`data-from`/`data-to`、时间顺序、图例和图下编号引用
R100: HTML 时序图须以居中标题、彩色参与方栏、左侧阶段标签、虚线生命线、来源圆形编号、消息标签和方向箭头建立视觉层次；长图底部重复参与方栏，主流程与异常使用可辨识的色彩和线型，悬浮与选中状态不遮挡箭头或改变时序位置
R101: 每条关键消息须在对应图下说明中提供结构化预览字段，至少包含调用或动作、关键业务数据和结果；悬浮详情只读取同编号说明，不另存一份可能失配的业务事实，完整依据仍在图下
R102: 详情须支持鼠标悬浮、键盘聚焦、点击固定及触屏点按，提供关闭与跳转完整说明的入口；弹层须避开视口边缘，在窄屏内可滚动，筛选或滚动后不得遗留失效详情
R103: 开始前须按文档模式和用户目标确定业务流程、模块、时间或版本基线及明确排除项；范围不明且会改变结论时须先澄清
R104: 按已确定范围遍历入口、调用方与被调用方、分支和异常路径、数据读写、配置、接口契约及相关项目文档；需求设计还须核对受影响的现有流程与验收条件，记录未覆盖处及原因，发现问题后仍须完成范围内检查
R105: 范围内检查完成后须一次性整理完整的现状说明或需求设计，列出覆盖范围、可定位依据、全部有证据的发现、未覆盖处与待确认项；中途可报告覆盖进度，不得把先发现的几项作为最终结论
R106: 成稿前须按项目规则 R111 核对需求与功能设计关键词，在正文主流程前列出术语、定义、适用场景与设计依据；同词不同义须列明区别，缺少设计依据的定义标为待确认，不得凭空命名
R107: 文档中的旧版、新版节点仅用于项目已确认的正式线上主分支固定提交与本次任务结果的对比；同一功能分支内的多轮修改须记录为迭代，不得各自定义为旧版和新版
R108: 本次范围确有需要展示的类、组件或状态关系时，须按实际问题绘制对应 UML 类图、组件图或状态图，呈现对象、职责、关系方向及边界；无相关关系或图无助于理解时省略，不为凑图虚构类型或状态
R109: 本次范围确有需要展示的表关系时，须绘制 SQL 表关系图，标明实际或拟议表、主键、关联业务键或外键、关系基数及关键约束；无相关表关系或图无助于理解时省略，未建立物理外键时不得将业务关联标为外键
R110: 已绘制的 UML 或 SQL 表关系图须以稳定编号关联主时序消息及图下依据，区分现状与拟议变更；输出前核对名称、方向、键、基数和版本与源码、迁移 SQL、项目文档及正文一致，无法核实的关系标为待确认
R111: 每次生成、修订或移除现状说明或需求设计 HTML 后，须以 `references/design-index.html` 为底稿更新 `docs/overview/design/requirements-index.html`；若该路径已有不带 `kaka-requirements-designer:index` 标记的页面，保留原文件并改用 `docs/overview/design/requirements-catalog.html`，备用路径同样被非规范页面占用时须先报告冲突，不得覆盖。新详情页须保留 `kaka-requirements-designer:detail` 归属标记；扫描各模块默认输出目录时只自动收录带该标记的页面，并收录本次明确由本规范生成的自定义输出。旧索引中的无标记页面先核实归属，未核实时保留原索引并报告待确认，不得自动增删其入口；仅为实际存在的 HTML 建立按文档类型分组的入口，不保留失效链接或覆盖非本规范内容
R112: 每个设计详情页须提供返回实际主页面的可点击链接；同一磁盘内双向链接使用相对路径，跨盘自定义页面使用 `file:///` 本地绝对 URL 并注明仅在当前机器有效；主页面与详情页须在离线打开时可双向跳转，不能仅依赖浏览器历史记录
R113: 需求设计须在同一 HTML 展示与本次流程和变更范围对应的设计类图；确无类级设计时须在类图区说明不适用及依据，不得虚构类填图
R114: 设计类图须按项目与模块列出相关类或接口的职责、关键属性与方法，并区分现有、拟议及新增、修改、沿用状态；现有成员须有源码依据，拟议成员须有关联需求或设计依据
R115: 设计类图须显示类间实际或拟议的依赖、关联、继承、实现或组合关系，标明方向、关系类型及已知多重性；不得从调用关系臆造继承、组合或字段
R116: 类和关系须使用稳定编号，与涉及的时序消息、图下实现映射及验收条件双向定位；修订时同步核对类名、成员、关系端点和编号引用
R117: 现状说明仅在范围内存在可核实类结构时展示现有类图，不得把拟议类混入现状；两种模式的类图在桌面和移动端均须可读且离线可用
R118: 用户另行要求保存 UI 线框、原型、界面规范或评审材料时，按项目规则 R141 分别归入 `docs/{module}/design/ui/wireframes/`、`docs/{module}/design/ui/prototypes/`、`docs/{module}/design/ui/specs/` 或 `docs/{module}/design/ui/reviews/`；需求说明仍归 `docs/{module}/requirements/`，正式前端源码与资源仍由项目正常版本管理，不将 UI 分类视为自动生成或实现授权
R119: 需求设计须按 [项目文档与功能状态规范](references/project-documentation.md) 区分需求结论、界面与技术文档及功能实现证据；在同一 HTML 汇总功能或验收项的代码、测试和发布状态，不能以源码存在推断测试通过或线上使用。现状说明无交付目标时不虚构完成状态

## 工作流

```
Step 0: 按 R103 确认现状说明或需求设计模式、主题、范围、基线与已有材料，按 R014 核对输出分类及任务 worktree 或项目指定主分支
Step 1: 读取相关 project-spec、源码、接口和数据库结构，按 R104 遍历范围内关联处，列出已核实事实、现有实现、未覆盖处与待确认项
Step 2: 按项目分栏梳理参与模块、实际交互时序、通信与数据流、并发条件及表的读写关系；按 R108–R109 确定适用的其他 UML 与 SQL 结构图，需求设计再按 R113–R115 核对设计类、成员、关系、变更和依据
Step 3: 先按 R106 编写关键词定义，再编写离线 HTML 主时序图、需求设计类图、按编号附着的说明及适用的其他 UML 与 SQL 表关系图；完成筛选及类与消息的双向定位
Step 4: 按 R111–R112 更新设计主页面和详情页返回链接，再按 R110、R116–R117、R119 静态核对图间关系、项目事实、功能状态及适用验收条件，检查桌面和移动端的主时序、结构图与筛选视图
Step 5: 按 R105 核对范围覆盖，逐项打开主页面与详情页验证跳转和返回，交付主页面及完整 HTML 的路径、关键结论、未覆盖处与待确认项；实现交由 coder
```
