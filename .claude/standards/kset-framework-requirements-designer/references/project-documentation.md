# 项目文档与功能状态规范

> project-init 生成。本文件约定项目内需求、UI/UX、技术设计和业务功能状态的交付口径；init 只生成规范，不预建实际业务文档。执行约束以 [项目规则](../../../rules/kset-framework-project-rules.md) 为准，项目事实以 [project-spec](../../kset-framework-coder/references/project-spec.md) 为准。

## 共用边界

R001: 先核对项目已有正式文档和用户指定位置；同一功能沿用稳定 `feature-key` 与已有需求、界面、技术和变更记录，不另建平行权威文件。无既有位置且用户要求保存时，按项目规则的产物分类确定路径与 Git 类别
R002: 实际生成的文档须说明主题、适用范围、依据或来源、当前结论与待确认项；负责人、版本、时间和验收证据仅在可核实时填写，不编造 owner、发布状态或验证结果。草稿、正式契约和已运行事实分别标明
R003: 需求结果、界面状态、技术实现和验收项通过稳定的功能、场景或节点编号互相定位；只在事实所有者处维护定义，其他文档引用其位置。上游结论变化时核对受影响的下游内容和链接，仅更新实际受影响处
R004: 下列文档按任务及项目适用性生成，缺少界面、跨模块设计或运行证据时不创建空文档或虚构阶段；静态分析不能证明测试、发布或线上使用

## 需求与业务文档

R005: 需求设计由 `kset-framework-requirements-designer` 按 `requirements-format.md` 生成离线 HTML；产品侧 PRD 按 [项目 PRD 规范](../../../standards/kset-framework-prd.md) 与项目既有格式编写。记录目标与使用者、范围内外、触发与可观察结果、主流程与适用异常、规则来源、验收条件及未决项；已有实现与拟议行为分开

## UI/UX 文档

R006: 涉及界面且用户要求保存 UI/UX 文档时，按 [项目 UI/UX 规范](../../../standards/kset-framework-ui-ux.md) 或项目已选文档交付契约处理；须关联需求或场景编号，说明目标用户与任务、页面及导航、操作与反馈、加载/空/失败/成功等适用状态、恢复、响应式和无障碍要求，并记录素材来源与适用的实际视口验证结果。无界面任务标为不适用

## 技术设计文档

R007: 用户要求保存技术设计时，由 `kset-framework-technical-designer`（已生成时）或本次获授权的设计角色核对项目现有文档位置；说明目标与已确认约束、事实所有者与模块边界、关键业务结果、接口和数据契约、必要的一致性与失败处理、兼容及迁移影响、适用的性能与可观测要求、可执行的验收条件及待决项。方案取舍记录依据和后果；ADR 仅在需长期追溯的重要决策时建立，不预设事务模式、中间件或测试命令

## 业务功能实现情况

R008: 需求设计的“实现映射与完成情况”以功能或验收项为单位汇总需求编号、设计位置、实现位置及代码状态，并分别记录测试、发布或线上使用的证据与状态。代码可见、验收通过、已发布是不同结论；缺少证据时写未验证或待核实，不能由源码存在推断完成上线
R009: 同一功能后续改码时，只有已存在且内容受影响的需求、UI/UX 或技术文档才按项目规则同步；多轮实现替换另按 `feature-change-record-spec.md` 记录代码入口、替代关系与回滚来源。功能状态汇总不替代变更历史或实际测试报告

## 来源与生命周期

R010: 规范来源、项目事实和业务文档各保留权威位置；本文件与项目 PRD、UI/UX 规范是只读的 init 参考快照，实际文档是按任务维护的输出，不得将 AI 生成来源当作 Git 或权威性判据
R011: 文档按实际事实标记草稿、待评审、已确认或已发布，并记录来源、适用范围和确认依据；状态表示文档自身，不代表代码实现、测试或线上发布。无审批流程时不虚构评审人或发布阶段
R012: 已确认或正式交付文档更新时，沿用原文件与稳定编号，记录受影响的上游依据、下游引用和变更原因；AI 规则产物按项目根 `artifacts/` 的 generated、staged、published 生命周期处理，运行审计仅在真实使用时记录，不能凭目录存在推断审批或使用事实
