# 项目逻辑与需求设计 HTML 成稿结构

> 本文件是项目规范的内部格式说明；现状说明交付为 `docs/{module}/reports/logic-{feature-key}.html`，需求设计交付为 `docs/{module}/requirements/{feature-key}.html`。同一功能沿用项目规则 R140 的稳定文件键；每次成稿须填入目标项目的实际信息，不保留示例或占位符。

## 设计主页面与导航

`docs/overview/design/requirements-index.html` 是默认统一入口，以 `design-index.html` 为底稿并保留 `kaka-requirements-designer:index` 归属标记；若已有不带标记的同名页面，保留原内容并使用 `docs/overview/design/requirements-catalog.html`。新详情页保留 `sequence-page.html` 中的 `kaka-requirements-designer:detail` 标记。生成、修订或移除详情页后从仓库根扫描 `docs/*/reports/logic-*.html`、`docs/*/requirements/*.html`，只自动收录带详情页标记的文件，并核对本次明确由本规范生成的自定义输出；旧索引中的无标记页面先核实归属，未核实时保留原索引并报告待确认，不自动增删入口。仅保留实际存在的 HTML，按文档类型列出页面，标题取实际主题。默认目录与主页面同盘时使用相对 `href`，详情页按主页面真实位置计算返回路径；跨盘时双向使用 `file:///` 本地绝对 URL，并标明仅在当前机器有效。无页面的分组可省略，不得展示失效链接。离线打开主页面后逐项核对进入和返回，不用 `history.back()` 代替返回链接。

## 页面顶部

以主题为居中标题，下方紧凑列出文档类型（现状说明或需求设计）、目标项目、涉及模块、整理日期、范围与当前待确认项数量。关键词定义紧随顶部信息，其后进入主时序图与适用的结构图，不放功能介绍或装饰性首屏。参考样式只用于版式、层次和配色，不借用示例图中的参与方、步骤、类、表或业务判断。

## 关键词定义

只列理解本次需求或功能设计必需的业务术语，优先沿用项目已有定义。每个定义关联可定位的需求或功能设计依据；现有实现只用于核对事实，不替代设计依据。同词不同义分别列出并说明适用范围与区别；缺少设计依据的含义写“待确认”，不得凭空造词或用含糊名称代替定义。

| 关键词 | 定义 | 适用功能或场景 | 需求或功能设计依据 | 同名定义的区别 |
|--------|------|----------------|------|----------------|
| 实际业务术语 | 可核实的业务含义 | 相关流程或节点 | 可定位的需求或设计位置 | 无或具体区别 |

## 主时序图

按项目分栏绘制一张 HTML 主时序图：项目是外层栏位，模块是栏内参与方和生命线，交互按时间自上而下排列。根据实际流程将连续消息划为少量有名称的阶段，左侧显示阶段序号与名称；阶段名不预设业务步骤。顶部用不同浅色的参与方标题，向下延伸虚线生命线，消息从来源生命线指向目标生命线并在来源处显示圆形编号，底部重复参与方标题以便核对长图。消息行表达触发条件、调用方与目标、分支、异常处置和结果；领域、项目与包、数据存储及变更信息通过编号说明叠加。类、组件、状态和表关系在下方对应结构图中展开，不复制流程路径。图下表格用于展开依据与细节，不能代替图上缺失的路径。

成稿以同目录 `sequence-page.html` 为页面结构参考，直接编辑 HTML：`.participants.top .participant` 按项目及模块顺序列出参与方，`.participants.bottom` 以相同顺序与色标重复；`.phase` 包住连续的 `.interaction`，`.phase-label` 写真实阶段；`.interaction` 按业务时间顺序排列，以 `id` 保持消息编号，以 `data-from` 和 `data-to` 指向从 1 开始的参与方序号，以 `data-category` 声明适用筛选类别。消息标签写短动作、通信方式和关键数据，`#note-编号` 写完整依据与说明，说明元素使用相同的 `data-category`。增删参与方时须同步核对顶部、底部、生命线和所有消息端点。删掉页面示例和默认说明，按实际实现或已确认设计填充。

时序图按项目首次出现顺序排列栏位，栏内按模块顺序排列生命线。HTML 消息行在文档中的先后即业务时间顺序；同层并行事件须以条件或异步标签说明。消息箭头保留来源与目标、编号、方式及数据摘要；请求、响应、投递、消费、异常和补偿都按实际发生顺序放置。跨项目调用不能放到错误项目栏，读写数据须连接到实际负责模块或存储参与方。无法核实的时序、项目归属或数据来源写“待确认”，不得用排版猜测补齐。

附加说明和数据按编号附着于主时序图：图上只放业务键、状态/数值变化、读写动作或关键结果的短摘要；图下对应 `id="note-编号"` 的说明展开来源、转换、权威落点、依据、边界、异常结果及待确认项，并可通过 `href="#编号"` 返回消息行。UML 与表关系图使用自身稳定编号，并关联相关消息及说明；不把全部字段堆在消息标签上。

每条关键消息使用 `button.label[data-note="note-编号"]` 关联同编号说明；对应说明内的 `.preview-data` 用 `dl` 列出调用或动作、关键业务数据和结果。页面在悬浮或键盘聚焦时复制这份结构化摘要到详情弹层，点击后可固定，触屏点按可打开；弹层提供关闭和跳转完整说明入口。预览不独立维护业务事实，改动数据时只更新图下同编号说明并核对消息短标签。

成稿是 HTML 源文件，不提供画布编辑或导入导出工具。修改参与方、消息、类、关系、结构图、样式和图下说明时直接编辑 HTML；CSS 绘制生命线、结构框和关系线，浏览器负责离线展示、缩放与横向滚动。少量内嵌脚本只计算消息在参与方之间的位置并筛选类别，不承载业务事实。修改后须核对消息及结构图编号、依据、版本映射与验收条件，不能让图与正文失配；禁止使用 Mermaid、SVG/Canvas 画布或外部画图工具生成图形。

| 类别 | 图上内容 | 默认底色 |
|------|----------|----------|
| 主流程 | 业务动作、参与方、条件与结果 | 白色 `#fff` |
| 异常与恢复 | 失败触发、重试、补偿、人工处理及最终结果 | 浅玫红 `#fff0f2` |
| 通信路径 | Web HTTP、直连 RPC、消息投递等跨边界连线 | 浅杏 `#fff0e1` |
| 数据流 | 关键数据的来源、转换、传递、落点与对外结果 | 浅金 `#fff5d9` |
| 并发控制 | 业务并发条件、锁及其他保护方式 | 浅珊瑚 `#ffe9df` |
| 领域 | 领域对象、边界及关系 | 浅莓红 `#fcebf2` |
| 项目与包 | 项目、模块、包及负责的执行逻辑 | 浅葡萄 `#f5eafa` |
| 数据存储 | 数据库、实际表名、读写方向 | 浅琥珀 `#ffefce` |
| 变更状态（仅需求设计） | 新增、修改、沿用、移除及完成情况 | 浅红 `#ffe3e7` |
| 评估建议（需求设计或明确要求评估） | 冲突、优化点及待决策项 | 暖灰 `#f5ede9` |

类别选择控件包含“全部”和当前模式适用的类别。筛选只改变同一张图的可见内容；单类别视图仍保留相关主流程节点和连线。背景、说明框、类别标题和图例使用一致的类别映射，不仅靠颜色表达含义。

类别筛选与消息编号锚点用于定位；浏览器原生缩放和横向滚动用于查看较宽的时序图。筛选后仍须保留必要主流程上下文，目标在当前类别中不可见时可切回“全部”。桌面和移动端的控件不遮挡参与方、消息或图例，缩放后仍能辨认文字和方向。页面所需 CSS 与少量布局脚本均内嵌，离线打开仍可使用。

视觉布局须使标题、阶段、项目参与方、时间顺序、消息方向和结果一眼可辨：桌面阅读区居中并限制最大宽度，参与方较多时按约 168px 的单栏宽度计算图宽，仅让图表区域横向滚动；图下说明使用更窄的正文栏。阶段栏与泳道分开，参与方栏保持稳定高度，编号圆点与来源生命线重合，箭头端点与目标生命线重合；短标签放在连线上方，保持清晰对比和可见焦点，不得截断文字或压到下一行。类别与异常路径同时用文字及线型区分。详情弹层避开视口边缘，窄屏限制高度并允许滚动；悬浮、聚焦、点按、关闭、筛选和滚动后均检查弹层内容与当前编号一致，不能遮住正在阅读的消息或图下锚点。

颜色分两层：上表的类别浅色底表达信息类别；实体色标表达身份。页面以白底和深灰线条表示主流程，参与方使用可区分的浅蓝、浅黄、浅红、浅绿等色标，阶段标题使用对应的较深色；异常使用深红色，异步使用琥珀色，圆形编号使用金黄色，颜色语义不得混用。同一领域内的对象共用领域色标，不同领域使用可区分的色标；同一项目包在所有节点保持同色，不同包可区分；同一数据库表在所有读写位置保持同色，不同表可区分。项目、模块、包或表数量较多时，优先用色标加名称、图例及分组边界辨认，避免仅凭相近颜色区分。色标不替代“读/写”、实体名称和类别标题。

跨模块调用、依赖或数据引用须让来源模块与目标模块各自保持固定且不同的身份色标；引用连线两端分别标出对应模块色标，图例按模块名称列明颜色与适用范围。相同模块在完整视图、筛选视图和版本分支中保持同色；连线箭头与短标签继续说明引用方向和关系类型，模块色标不得代替通信方式或新增、修改、移除的变更标记。

流程图先按可定位的现有实现核对入口、调用顺序、条件分支、异常路径和结果，再绘制实际路径；拟议行为明确标注，不与已实现路径混写。同一父节点的平级分支尽量在同一列或同一行并排，分支条件放在出口，汇合点放在分支之后；交叉线、回流线和异常线要能辨认方向。布局受屏幕宽度限制时可纵向排列，但保持相同层级和编号对应关系。

每条适用的异常支路从发生点出发，经过失败判定与重试、回滚、补偿或人工处理节点，到达可观察的成功、失败或待处理结果；不能只画一个“异常”终点。现状说明按已核实的实现绘制现有自动恢复或人工处置；无法核实的处置标“待确认”，不得因缺少新增自动修复承诺而改写现有行为。需求设计涉及系统重启、服务发布、RPC 断联及 MySQL、Redis、MQ 等低概率基础设施故障时，未有已确认自动修复承诺的残留流程或数据问题在设计结论中明确写“暂由人工处理”，列出业务键、定位依据、责任方、处理入口与结果核验；仅在已确认要求系统自动修复时设计新增自动恢复路径。超时、远端失败、消息投递或消费失败、并发冲突等仅在现有实现可核实或新需求明确时绘制。异常连线标明触发条件和方向，图上短标签概括处置，点按详情与图下异常表写依据、次数或时机及责任方；拟议处置标“拟议”。

视觉优先级按业务结果影响、数据一致性风险和使用者关注度确定：主流程与会阻断结果或造成错误状态的异常使用清晰且较强的节点、文字和连线；可恢复的次要异常采用较轻的线型与色调；项目包、表、调用参数等支持信息保持紧凑，默认通过点按展开。弱化只减少视觉权重，不隐藏实际异常、最终结果或必要的触发条件；筛选后仍能从主流程定位每条异常支路。不同层级依靠标签、线型和图例共同表达，不只靠透明度或颜色。

跨项目或跨进程连线标明方向及“Web HTTP”“直连 RPC”“消息投递”等实际方式，并标注同步或异步；同一图中以线型或简短标签区分请求、响应、投递与消费，不把投递画成同步调用。HTTP 标出调用方、入口路径与方法，RPC 标出调用方、服务与方法，消息标出生产者、主题或队列、消费者及消费触发点；只显示已核实的信息，细节在图下通信路径表中按连线编号给出依据。重试、超时、回调、失败补偿或投递成功与业务完成的区别，仅在相关路径存在或设计明确要求时说明。

关键业务数据沿同一张图中的流程节点与已有通信连线标注，不另画平行数据图：从用户输入、消息或上游表等来源开始，经过关键计算、字段转换或状态变化，再到权威表、下游消息及对外响应。数据流使用稳定编号和方向箭头，在线旁以短标签写数据名及“产生”“读”“写”“投递”“消费”等动作；通信方式仍由通信层表示，避免两条边重复指向同一目标。仅画影响业务结果的数据及关键转换，字段明细放入点按说明和图下表；来源、转换或落点证据不足时在对应位置标“待确认”。

涉及同一业务键的并发写入、重复请求、重复消费或定时任务重叠执行时，在关键节点旁显示紧凑的小锁标识和“锁”文字，点按后查看锁类型、业务键、范围、获取与释放时机、失败结果及依据。仅已核实使用或方案明确拟议使用互斥锁的节点显示锁标识；无锁写“无锁”，证据不足写“待确认”。唯一约束、条件更新、版本号及事务按各自机制标注，不用锁图标代替。新设计中的保护方式标“拟议”，不写成现有实现；不涉及并发风险的节点无需逐个显示“无锁”。

需求设计调整既有流程时，共用动作沿一条主线自上而下排列，每个动作只画一次。仅从发生变化的位置切出版本分支，并在入口标明版本与变化条件；不要为了左右对称复制共用节点或添加空分支。

若只新增新版功能，旧版用标明版本的连线绕过新增节点，直达下一个共用节点；若两版都变化，再并列展示各自的局部路径。后续行为相同时汇入一个共用节点，后续结果不同时分别结束。旧版仅以项目已确认的正式线上主分支上有发布或部署证据的提交源码为依据，记录分支名及本次任务首次固定的完整 Git SHA；仅在主分支开发的项目还须记录目标环境实际使用的正式发布版本及其与提交的对应关系。同一任务多轮迭代沿用该 SHA，无法确认适用的已发布基线时标“待确认”，不以分支 HEAD 或开发过程中的先前修改充当旧版；移除项标在旧版，新增和修改项标在新版。

| 路径 | 节点编号 | 连线编号 | 数据流编号 |
|------|----------|----------|------------|
| 共用主线 | `SHARED-N01` | `SHARED-E01` | `SHARED-D01` |
| 旧版差异 | `OLD-N01` | `OLD-E01` | `OLD-D01` |
| 新版差异 | `NEW-N01` | `NEW-E01` | `NEW-D01` |

每类编号独立递增；图例将前缀对应到实际版本或共用范围。只有一条流程且不比较版本时可沿用单流程编号。已使用的编号在文档修订时保持稳定，新增内容在所属路径追加编号。

旧新版的替换、拆分、合并、移除和新增关系以完整编号逐项映射；相同序号不代表同一动作。图、说明表、验收条件及定位链接使用同一套完整编号。更新已有 HTML 时，同步修改旧式 `N01` 编号的全部引用，不混用新旧编号格式。

变更范围用带“新增”“修改”或“移除”文字标签的浅色边框或背景包裹受影响节点、连线和说明框；三类变化使用可区分的边框色或线型，并在图例中对应说明，不能只给单个文字上色。修改项同时包住旧行为与新行为的对应片段，移除项保留可辨认的旧路径。变更色只表示变化，领域、包和表的身份色标继续显示。沿用项不使用变更强调色，完成状态另以文字和图例表达，避免把“已完成”误读为“新增”。

评估项贴在需要处理的节点、连线或流程片段旁，用稳定编号和“冲突”或“建议”短标签指向受影响位置；涉及两条相互冲突的路径时，同一编号关联双方。高优先级表示阻断验收、造成错误业务结果或数据不一致；中优先级表示影响关键使用或故障恢复；低优先级表示局部效率或表达改进。高影响冲突保持可见的边框与短标签，低优先级建议使用较轻的虚线标记，点按后展开依据、影响、建议和取舍；标记不得覆盖节点文字或连线方向。评估层与变更层分别筛选，待决策建议不能画成已确认的新流程。现状说明仅在用户明确要求评估时显示建议，且实际路径仍以源码依据为准。

节点文字使用简短业务动作、接口名或服务方法名；不展示类的全限定名。项目、模块、包和表名放在相关说明框中，数据库连线标注“读”或“写”。节点尺寸须稳定，长名称在图中缩略，完整名称通过悬浮、点击或触屏点按查看。

现状说明模式展示实际入口、调用路径、分支、异常处理、数据读写和对应源码依据；逐节点区分“代码可见”“未发现实现”“待核实”。代码可见的行为不自动标为生产已运行或验收已完成。没有本次交付目标时，本次变化与交付完成状态写“不适用”。

需求设计模式把变更类型与完成状态分开标记。已有实现的修改节点展示原有行为、本次行为和影响范围；已完成节点关联实现位置与满足的验收条件，未完成节点关联剩余工作与阻塞事项。无法核实的事实显示“待确认”。旧版与新版路径的编号、版本或适用时点及变更范围须与图下实现映射和验收条件一致。

## 设计类图

需求设计模式在同一 HTML 的时序图之后、图下项目说明之前展示与本次业务流程对应的设计类图。选取承载本次新增或修改行为的类、接口及理解关系所必需的沿用类；类图不是全仓类清单。若范围内确无类级设计，保留本节并写明“不适用”及依据，不为凑图虚构类。现状说明模式仅在源码或已确认项目资料可核实类结构时展示现有类图。

以 `sequence-page.html` 的 `.class-design` 为结构参考：`.class-grid .class-box` 每个类或接口只出现一次，标题标明类名、接口类型、项目、模块、包与“现有”或“拟议”；成员区只列影响本次设计的关键属性和方法及其类型、返回语义，不罗列全部代码。类框以稳定 `CLS-01` 编号定位；新增、修改、沿用为单独文字状态，不能用颜色代替。现有成员标明源码 `路径:行号`，拟议成员关联需求或功能设计依据，未确认的名称、类型或职责标“待确认”。
