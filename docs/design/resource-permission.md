# 资源权限规范

状态：**设计规范**（2026-08）。本仓尚未提供实现。业务仓与后续框架实现均须遵守本文；实现细节不得改变本文语义。

本文约定「对某条资源能不能做某个操作」。登录「你是谁」见 [登录鉴权](../usage/auth.md)。功能码「能不能进这个接口」仍用现有 `@RequirePermission`。

## 1. 目的

多产品共用同一套判定语义和数据形状，避免每个业务自己发明权限字段、权限 SQL 和互不兼容的角色模型。

本规范管三件事：

1. 一条授权长什么样
2. 一次判定怎么得出允许或拒绝
3. 业务允许扩展什么、禁止改什么

本规范不管：用户注册、角色菜单后台、具体资源类型（文档/订单等）、管理界面。

## 2. 术语

| 词 | 含义 |
|----|------|
| 身份 | 当前请求里的登录用户，本仓即 `LoginUser` |
| 功能码 | 全局能力名，如 `order:create`。无资源实例维度 |
| 资源 | 有类型、有实例编号的业务对象，如某张订单 |
| 操作 | 对资源做的动作，如读、写、删、执行 |
| 授权条目 | 把某些操作授给某个人或某个角色，可带过期和拒绝 |
| 使用维度 | 对资源本身做事（读内容、改内容） |
| 管理维度 | 对资源做管控（分享、发布、审核）。无管理条目即无管理权 |
| 规则链 | 按固定顺序跑的判定步骤，先得出结论就停 |

## 3. 两平面

```
身份（LoginUser）
    ├─ 功能平面：功能码 → 接口能不能进
    └─ 资源平面：类型 + 实例 + 操作 → 这条资源能不能动
```

| 平面 | 回答的问题 | 现有入口 | 本规范 |
|------|------------|----------|--------|
| 功能 | 这个人有没有「创建订单」这种全局能力 | `@RequirePermission("order:create")`、`LoginUser.permissions` | 不改 |
| 资源 | 这个人能不能读 **订单 1001** | 无 | 本文 |

两条必须同时想清楚：有功能码无资源权，接口能进但数据要挡；有资源权无功能码，不应从管理接口绕过功能闸。

功能码**不得**带资源维度。不要发明 `order:1001:read` 这种功能码。实例差异只走资源平面。

## 4. 身份

判定只认当前 `LoginUser`：

| 字段 | 用途 |
|------|------|
| `userId` | 匹配「授给用户」的条目。字符串，不强求数字 |
| `roles` | 匹配「授给角色」的条目。角色编码字符串 |
| `permissions` | 只用于功能平面，资源判定**不读**功能码列表 |
| `tenantId` | 多租户产品应当把授权隔离在租户内；无租户的产品忽略 |

超管：由产品定义（例如角色 `super-admin`）。超管在资源平面**短路为允许**，拒绝条目压不住。超管操作应当记审计。未登录用户没有身份，功能闸按现有鉴权返回未登录；资源平面视为无任何允许条目。

异步任务、系统内部路径没有登录用户时，不得假装成某个用户去走资源判定。入口已经校验过的系统路径可以跳过资源平面，但必须在产品说明里写明。

## 5. 资源

资源由 **类型码 + 实例编号** 唯一确定。

| 项 | 约定 |
|----|------|
| 类型码 | 小写点分或单段英文，如 `order`、`doc.folder`。产品内稳定，跨产品不要抢同一含义的码 |
| 实例编号 | 字符串。数字 ID 写成十进制文本即可 |
| 父资源 | 可选。用于「对项目授一条，项目内资源生效」。父怎么解析由产品提供，不写进通用条目结构 |

禁止在框架或通用表里写死 `文档=2、目录=1` 这种枚举值。需要整数存储的产品在自己仓做码到数字的映射，对外 API 仍用类型码。

## 6. 操作

对外一律用小写英文字符串，存储可用位掩码。调用方不算位。

| 码 | 位（2 的幂） | 含义 |
|----|--------------|------|
| `create` | 1 | 新建（可与写合并理解） |
| `read` | 2 | 读 |
| `write` | 4 | 改 |
| `delete` | 8 | 删 |
| `admin` | 16 | 管理维度下的全管理标记 |
| `execute` | 32 | 执行（查询、任务、动作） |
| `export` | 64 | 导出 / 下载 |
| `share` | 128 | 分享 / 再授权 |
| `publish` | 256 | 发布 |
| `review` | 512 | 审核 |

产品可以只用其中一部分。某类型不支持的操作，登记时不要列出来；判定遇到未支持操作视为拒绝。

新增操作：在上表之后用更高位登记，并同步字符串码。位不够时存储从 32 位升到 64 位，码表不变。

## 7. 被授予者

| 类型码 | 含义 | `granteeId` |
|--------|------|-------------|
| `user` | 某个用户 | 与 `LoginUser.userId` 同一套 |
| `role` | 某个角色 | 与 `LoginUser.roles` 中的编码同一套 |

可以扩展 `dept`、`app-key` 等，但必须：类型码稳定、ID 字符串、判定时能从当前身份解析出是否命中。

角色改名等于断链：条目里存的是编码，不是角色表主键。用户删除后条目可惰性残留；用户 ID 不得复用，否则会继承旧授权。

## 8. 授权条目

一条授权只描述「谁 + 哪条资源 + 哪些操作 + 哪个维度 + 允许还是拒绝 + 何时过期」。

| 逻辑字段 | 说明 |
|----------|------|
| 资源类型 / 资源编号 | 见第 5 节 |
| 被授予者类型 / 编号 | 见第 7 节 |
| 操作集合 | 字符串码列表；存储为位 |
| 维度 | `use`（使用）或 `manage`（管理）。缺省 `use` |
| 拒绝 | 否=允许；是=拒绝。拒绝始终压过允许 |
| 过期时间 | 空=永久。到期后该条不参与判定。时间格式与本仓 API 一致：`yyyy-MM-dd HH:mm:ss`，时区 Asia/Shanghai |
| 租户 | 可选。多租户时必须有 |

同一资源、同一被授予者、同一维度、同一拒绝标记，最多一条。更新是改这一条的操作位和过期时间，不是再插一行。

合并规则：

```
有效操作 = （用户允许 ∪ 角色允许）− 拒绝命中的操作
```

允许之间是并集，个人不覆盖角色。「大家都有、就他没有」只能用拒绝条目表达。

管理维度没有默认基线：没有管理条目就是没有管理权。

## 9. 单点判定

输入：身份、资源类型、资源编号、操作、维度（缺省使用）。  
输出：允许或拒绝。没有第三种给调用方。内部规则可以「弃权」交给下一步。

顺序固定，不得调换：

1. **超管**：允许，结束
2. **拒绝条目**：当前身份命中该资源该操作的拒绝（未过期）→ 拒绝，结束
3. **允许条目**：用户条目与角色条目操作位取并，包含该操作 → 允许，结束
4. **产品规则**：继承、父资源通配、公开资源等。只允许「允许 / 拒绝 / 弃权」，不得改 1～3 的含义
5. **类型默认策略**：该类型登记为默认允许或默认拒绝。未登记的类型默认拒绝

全部弃权时视为拒绝。

公开资源、目录继承、项目通配都不是通用条目的字段，必须走第 4 步产品规则。

## 10. 批量判定

列表、检索、导出不得对每行做一次单点判定来拼最终集合。

批量结果是三种编号集合（均为字符串）：

| 集合 | 含义 |
|------|------|
| 拒绝集 | 命中拒绝条目的资源，始终不可用 |
| 受限集 | 该类型已有允许条目覆盖的资源（进入白名单模式的那些实例） |
| 允许集 | 命中允许条目的资源 |

对单个编号：不在拒绝集，并且（不在受限集，或在允许集）才算通过。这与单点第 2、3 步同义。

类型默认允许：未出现在拒绝集、也未进入白名单的实例可通过。  
类型默认拒绝：未进入允许集的实例不可通过。  
超管：不过滤。

产品规则（继承、父通配）若影响列表，必须提供与单点一致的批量算法，禁止只在单点生效、列表漏网。

## 11. 资源类型登记

每个产品自己登记类型，通用层不预置业务类型。

登记必须提供：

| 项 | 说明 |
|----|------|
| 类型码 | 稳定、小写 |
| 显示名 | 给人看 |
| 支持的操作 | 子集，来自第 6 节 |
| 默认策略 | 无允许条目时允许或拒绝 |
| 父类型 | 可选。有父类型时产品必须能解析父实例编号 |

模块卸掉后：该类型不再登记，旧授权条目惰性保留；再登记同一类型码即可恢复。

## 12. 与功能码怎么叠

推荐顺序：先身份，再功能码，再资源。

```
未登录 → 401
无功能码 → 403（功能平面）
无资源权 → 403（资源平面，文案与功能平面区分开更好）
```

读类列表可以没有「写」功能码，但仍必须做第 10 节过滤。敏感写操作两闸都要。

`@RequirePermission` 继续只表示功能码。资源闸用单独的入口（方法注解或显式调用），不要把资源编号塞进功能码字符串。

## 13. 禁止

- 禁止在业务表加 `can_read`、`owner_only` 这类与本规范并行的权限列来做最终判定
- 禁止业务 SQL 私自 join 授权表拼出与规则链不一致的结果
- 禁止用功能码表达某一条资源
- 禁止调用方直接传权限位整数（API/DTO 只用操作码字符串）
- 禁止把拒绝做成「优先级较低的覆盖」
- 禁止超管被拒绝条目挡住
- 禁止未过期检查就把过期条目当真
- 禁止在通用存储里写死某产品的资源类型枚举

## 14. 扩展（允许）

| 方向 | 要求 |
|------|------|
| 新产品资源类型 | 只加登记 + 薄封装，不改判定顺序 |
| 新操作码 | 登记码与位，旧条目高位为 0 即无该权 |
| 新被授予者类型 | 能从当前身份解析命中即可 |
| 父资源通配 | 产品规则，且单点与批量一致 |
| 继承 / 公开 | 产品规则 |
| 条件授权（时间段以外的 ABAC） | 现规范不包含；以后若加，须是条目上的附加条件，不得打乱第 9 节顺序 |

## 15. 存储契约

实现可用任意库，逻辑字段必须能表达第 8 节。MySQL 参考形状（列类型 DATETIME，与本仓 SQL 约定一致）：

| 列 | 类型 | 说明 |
|----|------|------|
| `resource_type` | VARCHAR | 类型码 |
| `resource_id` | VARCHAR | 实例编号 |
| `grantee_type` | VARCHAR | `user` / `role` / 扩展 |
| `grantee_id` | VARCHAR | 被授予者编号 |
| `permissions` | INT 或 BIGINT | 位掩码 |
| `perm_scope` | VARCHAR 或 TINYINT | `use` / `manage` |
| `excluded` | TINYINT | 0 允许 / 1 拒绝 |
| `expire_at` | DATETIME NULL | 空=永久 |
| `tenant_id` | VARCHAR NULL | 可选 |

唯一约束：租户 + 资源类型 + 资源编号 + 被授予者类型 + 被授予者编号 + 维度 + 拒绝标记。

授权变更后，批量缓存若存在，失效时间必须短到产品可接受（秒级）；规范不规定缓存实现。

资源删除不要求级联删授权。残留条目在编号不复用的前提下无害。

## 16. 调用形态（规范级，非本仓 API）

单点：`check(类型, 编号, 操作) → 允许/拒绝`  
过滤：`filter(类型, 操作, 编号列表) → 可见编号`  
授权：`grant / deny / revoke`，入参用操作码字符串，可带过期和管理维度  
有效权查询：给定用户，返回某类型下最终能做的操作（供管理端预览）

管理 HTTP 路径、页面不在本规范内。产品自己包接口时，请求体应对齐上述字段名（`resourceType`、`resourceId`、`granteeType`、`granteeId`、`operations`、`scope`、`excluded`、`expireAt`）。

## 17. 本仓边界

| 位置 | 职责 |
|------|------|
| 本规范 | 语义与数据形状的单源 |
| `kset-starter-auth` | 身份与功能码，不承担资源判定 |
| 业务仓 | 类型登记、产品规则、表落地、管理界面 |
| 未来若做框架实现 | 只允许做引擎、存储适配、通用注解；不得内置业务类型 |

当前**没有**资源权限 Starter。业务仓可按本文自行实现；日后框架实现不得与本文冲突。
